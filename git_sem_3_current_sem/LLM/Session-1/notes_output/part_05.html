Why "mug" breaks character-level BPE, and where byte-level BPE comes in

[1:05:48 – 1:07:05]
The concept

"m" is not in the 7-character vocabulary, so "mug" cannot be encoded. A real tokenizer would give an unknown token.

  • This is only because the toy corpus and 10-token vocabulary are tiny.
  • BPE solves most OOV issues, but not all: new languages or new domains may contain characters absent from the English corpus.
  • Hence "a lot of today's models are going towards byte-level BPE".
Intuition + layman analogy

A keyboard with only the letters b, g, h, n, p, s, u cannot type "mug". A keyboard with all 256 raw key codes can type anything, even if it has to type it slowly, one code at a time.

Common mistakes
  • Assuming BPE can never fail. It fails when a base character was never seen in the training corpus.
Professor emphasized
  • "A non-token [UNK] will be assigned to this word. But that does not happen in practice because here the example is a very small corpus."
  • The fix is explained after the Q&A on BPE.
"Non token" → [UNK] (unknown token), as on the slide.
Character-level BPE can still produce [UNK]. Byte-level BPE removes that failure.

Q&A: why is "un" in the vocabulary but "pu" is not? Minimum frequency

[1:07:07 – 1:09:05]
The concept

You do not just merge until you run out. You set a minimum frequency and a maximum vocabulary size.

  • A pair is merged only if its count is at least the minimum frequency (e.g. 2, 3 or 5). This is a hyperparameter.
  • Merges are built on the previous iteration. A pair can only be merged if it exists in the current segmentation.
  • A student pointed out that "pu" (count 12) could be added. The professor agreed: with minimum frequency 5, "pu" qualifies. The slide is just an example of the mechanism.
Scenario

1
Compare each count with the threshold 5. 20, 16, 15, 12 are all ≥ 5 → all four allowed
2
Raise the threshold to 15. 12 < 15 → "pu" is excluded; 20, 16, 15 ≥ 15 stay
min_freq = 5 → 4 mergesmin_freq = 15 → 3 mergesa higher threshold gives a smaller vocabulary
Professor emphasized
  • "It's not like you always have to pick the maximum frequency pair." There is a rule, a minimum frequency hyperparameter.
  • "You can only merge if those two characters come together in my corpus minimum two, three, five times."
Check the slide mechanics : once "un" is merged, the word "pun" becomes "p un", so the pair (p, u) no longer exists. In strict BPE "pu" would then not appear, so "pu" on the board is an illustration, not a result of the exact algorithm. "Ah, PU" = (p, u).
Minimum frequency filters out rare merges. The slide's exact merge list is only a mechanism demo.

Q&A: character order, pruning irrelevant tokens, exam example

[1:09:07 – 1:10:33]
The concept
  • Order matters: a merge keeps the order seen in the corpus. "ug" is possible, "gu" only if the corpus contains it.
  • There is no separate step to discard tokens that are irrelevant to a language. You handle this during pre-processing and corpus creation.
  • A full BPE example is in the question paper. The professor will upload it with the answer key.
Justification
  • BPE is purely statistical: it never needs to know what a token "means".
  • Because it does not filter by meaning, cleaning is done upstream. "Generally nobody does it that way."
Professor emphasized
  • "If GU is not there in the corpus, the algorithm will anyway not pick it up."
  • Question paper plus answer key will be uploaded, with a full BPE worked example. Practise it.
BPE merges only pairs that really occur, in corpus order. Clean the corpus before you tokenize it.

BPE recap with the two hyperparameters

[1:10:34 – 1:13:07]
The concept

min_freq

Smallest pair count that is allowed to merge. Example: 5. With 15, "pu" (12) would be dropped.

max vocab size (tokens)

Stop merging when the vocabulary reaches this size, e.g. 30,000 or 50,000.

  1. Pre-tokenize the corpus into words and count their frequencies.
  2. Start with single characters.
  3. Apply merge rules starting with 2-character pairs: ug (20), un (16), pu (12, if allowed).
  4. Then 3-character combinations built on the previous iteration: hug (15).
  5. Continue until max vocab size is reached.
Step-by-step computation: size of the toy vocabulary
1
Base characters. b, g, h, n, p, s, u = 7
2
Merges performed (min_freq = 5, per the board). ug, un, pu, hug = 4
3
Vocabulary size. 7 + 4 = 11 (the slide shows 10 because "pu" is not in its vocabulary)
size = base + mergesa stopping rule fixes the number of merges: max_vocab − base size
Professor emphasized
  • "I should have added minimum frequency in the slide. I will modify this slide later so every section benefits."
  • "Max vocab size in tokens is your hyperparameter."
"PU has come 12 times because I set min-freq = 5" and "min-freq 15 → PU will not become part of the vocab" are written on the slide.
BPE has two stopping controls: min_freq per merge and max vocab size overall.

Byte-level BPE

[1:13:13 – 1:15:13]
The concept

Same merge algorithm, but the base alphabet is the 256 byte values instead of characters.

Slide "Byte-level BPE". Board: "token-ID = next available".
  • Vocabulary is not made of characters but of bytes. Characters are decomposed into their UTF-8 byte sequence.
  • After the first merge the vocabulary records "ID 256 = bytes [117 103] = ug".
  • This removes the possibility of unseen characters. Many (not all) LLMs use it.
Scenario

Redo the toy example at byte level and encode "mug"

SymbolByte value
u117
g103
n110 computed
h104 computed
m109 computed
Step-by-step computation
1
Base vocabulary IDs. 0 … 255 = the 256 raw bytes
2
Merge 1: (u, g). ID 256 = [117, 103] = "ug"
3
Merge 2: (u, n). ID 257 = [117, 110] = "un"
4
Merge 3: (h, ug). ID 258 = [104, 256] = "hug"
5
Encode "mug". bytes [109, 117, 103] → apply ug → [109, 256]
6
Vocabulary size now. 256 + 3 = 259
mug → [109, 256]no [UNK]2 tokens instead of a failure
Justification
  • Every possible text maps to bytes, so there are no unseen characters.
  • Saves space: individual elements are just bytes (256 base entries).
  • Scripts that need several bytes per character (e.g. Hindi, 3 bytes) cost more tokens if the vocabulary has no merges for them.
complete coverage vs longer sequences for rarely merged text.
Professor emphasized
  • "Vocabulary is not based on characters but on bytes." Merged pairs get "the next available token ID" (board).
  • "UG, HUG, all of these tokens will get my token IDs."
"U is a character represented as a byte 117, G as 103" matches the slide. Board row: token IDs 0–7 with u, g, h, m, p, v, ug, hug (hand-written, illustrative).

BPE: advantages and limitations

[1:15:17 – 1:17:19]
The concept

Advantages (slide)

  • Efficient handling of rare words and subword units.
  • Reduces the vocabulary size, so the model is more efficient.
  • Better generalisation by breaking words into subword units.

Limitations (slide)

  • Can give fragmented tokens for languages with complex morphology.
  • May not capture semantic meaning as well as other methods.
Scenario

The "apolog-" family (professor's illustration)

WordPossible split Subwords
apologyapolog + y2
apologiseapolog + ise (she says "ize")2
apologistapolog + ist2
Step-by-step computation: vocabulary entries needed
1
Word-level: one entry per word form. 3 entries
2
Subword: shared stem plus 3 suffixes. 1 (apolog) + 3 (y, ise, ist) = 4 entries
3
Add more forms: modernise, modernist share their own stem, but the suffixes ise and ist are reused. adding "modern" costs 1 new stem, not 2 full words
savings grow with more wordsfor 3 words the saving is negative (4 > 3). It pays off when suffixes are reused across many stems
Justification
  • Each word form does not need its own vocabulary entry, so vocabulary stays small and rare words are covered.
  • Rules are simple frequency-based merges with no linguistic rules, so languages with complex morphology (South Indian languages, French) get fragmented tokens.
  • It does not capture meaning, only statistics.
simple, language-agnostic statistics vs poor fit for morphologically rich languages. Still, "BPE or some variant" is very popular.
Common mistakes
  • Believing BPE splits words at linguistic boundaries. The splits come from frequencies, not grammar. The "apolog + y" split is "just from heuristics, it depends upon your training corpus".
Professor emphasized
  • "Apologise, modernise: all of this will not have their own vocabulary."
  • Models trained on many languages see fragmented tokens, and BPE may not suit them.
"A POLOG" → apolog. "Y", "IZE", "IST" are the suffix pieces she named. "Ohh" and "So that's the kind of limitation" are filler.
BPE shares stems across word forms (good), but it is blind to grammar, so morphologically rich languages fragment.

SentencePiece and how libraries handle whitespace

[1:17:21 – 1:19:13]
The concept

You do not write BPE yourself. Use a library. SentencePiece (Google) implements BPE and Unigram LM.

  • Language-agnostic: operates on raw text, no pre-tokenizer needed. Works for unsegmented languages (Chinese, Japanese, Thai).
  • Backend of T5, Gemma, and Meta's Llama 1 and 2 (slide).
  • Unigram LM: single tokens (1-grams) used together. The professor says the main difference between libraries is how whitespace is handled.

WordPiece (BERT)## marks a continuationToken ## ization
Step-by-step computation illustrative
1
Mark word starts with ▁. "Tokenization matters" → ▁Tokenization▁matters
2
Split by learned pieces. ▁Token | ization | ▁matters
3
Count tokens. 3 tokens
4
Decode by joining pieces and turning ▁ back into a space. "Tokenization matters"

Justification
  • Treating whitespace as a normal symbol makes tokenization reversible and works for languages without spaces.
BPE with a pre-tokenizer is simple but assumes spaces separate words. SentencePiece drops that assumption.
Professor emphasized
  • "How this algorithm is actually used: you don't have to write any such algorithm. We have libraries."
  • These outputs ("Ġ" prefix) will be visible in webinar 1.
  • To train a new tokenizer or extend an existing one, use the open-source tokenizer in Hugging Face.
"G test" / "G tasty" → Ġtasty. "Lama and Quen" → Llama and Qwen. "Sentence-based library" → SentencePiece.
Extra reading
  • Hugging Face: SentencePiece and WordPiece sections: SentencePiece treats text as a raw stream and uses ▁ for spaces. Fetched and checked.
Use SentencePiece or Hugging Face tokenizers. Libraries differ mainly in how they mark whitespace (▁, Ġ or ##).

Hugging Face tokenizer library, per-document counts, "256 bytes" clarification

[1:19:19 – 1:21:17]
The concept
  • Frequencies across documents: "hug" can appear in many documents. Counts are combined over the whole corpus, either before or after the split. The result is the same.
  • Why 0–255? A byte has 256 values (0 to 255). BPE (character level) does not use bytes. Byte-level BPE uses all 256 as individual symbols.
  • Rare words such as "tasty" written with many a's are split into subword parts by BPE.
  • Hugging Face will be used "extensively". The tokenizer library is demonstrated in webinar 1.
Scenario

("hug", 10)same totals whether you merge counts first or pair counts first

🧠 Quick recall

1. Why can BPE still produce [UNK], and what fixes it?
If a base character never appeared in the corpus (e.g. "m"), it is not in the vocabulary. Byte-level BPE starts from the 256 bytes, so every string is encodable.
2. Name the two hyperparameters of BPE training.
Minimum frequency (smallest pair count allowed to merge) and maximum vocabulary size (stop when reached).
3. In byte-level BPE, "u" = 117 and "g" = 103. What is the ID of the merged token "ug" and what does the vocabulary store?
ID 256 (the first free ID after 0–255), recorded as bytes [117, 103] = "ug".
4. Give one advantage and one limitation of BPE.
Advantage: handles rare words and shrinks vocabulary by sharing subwords. Limitation: frequency-based merges fragment languages with complex morphology and do not capture meaning.
5. How do SentencePiece, byte-level BPE and WordPiece each mark word boundaries?
SentencePiece: leading ▁. Byte-level BPE (GPT, Llama, Qwen): leading space shown as Ġ. WordPiece (BERT): ## on continuation pieces.
