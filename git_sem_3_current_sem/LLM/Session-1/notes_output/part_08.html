What BPE produces and what the embedding layer produces

[1:53:02 – 1:54:45]
The concept

BPE only tokenizes. Embeddings come from the embedding layer.

  • BPE has two jobs: trainer (builds vocabulary and token IDs) and segmenter (splits new text).
  • Token IDs are fixed: "fox" might be, say, the 50th entry and stays so.
  • Implementations differ: a library may wrap extra code around BPE. With Hugging Face open models you get tokenization first. With a hosted API such as OpenAI's you send text and the pipeline in between is hidden.
Intuition + layman analogy

BPE is the librarian who assigns shelf numbers (token IDs) to every book. The embedding layer is the reader's notes on each book (vectors), written while learning, not by the librarian.

Common mistakes
  • Asking "are token embeddings the output of BPE?" No. BPE outputs tokens and IDs only.
  • Mixing the library's output with the algorithm's output. A wrapper may return more than the algorithm itself.
Professor emphasized
  • "BPE trainer and BPE segmenter." "BPE's job is only this, because BPE is a tokenizer."
  • Student Powar Sagar Ganpati confirmed the final step: token embedding plus positional embedding goes to the Transformer. Professor: "Yes, you are correct."
"BP" / "bdb" → BPE. "open ID" → OpenAI. "DP as a tokenizer" → BPE as a tokenizer.
BPE: text → tokens → fixed IDs. Embedding layer: IDs → vectors. They are different components.

The same tokenizer must be used, and unknown tokens still happen

[1:55:13 – 1:55:57]
The concept

The tokenizer used at inference must be the one used to train the embeddings. Otherwise the vector is unknown.

  • If a rare token is not in the vocabulary, an unknown / out-of-vocabulary token is still produced. This remains possible with ordinary BPE.
  • Byte-level BPE removes this failure (parts 04 and 05).
Scenario

What happens with a tokenizer mismatch?

Same tokenizer as trainingID 7 → row 7 of E, the vector learned for "the"
Different tokenizerID 7 may mean another word, so the model sees the wrong vector
Unseen word, non-byte tokenizer<|unk|> ID, no information about the word
Professor emphasized
  • "Otherwise it will generate an unknown token. If some rare token is not part of the vocabulary, an unknown or out-of-vocabulary token will still be generated."
Tokenizer and embedding table are a matched pair. Mismatches or OOV words break the lookup.

Who decides whether a word splits into two or three subwords?

[1:56:00 – 1:56:37]
The concept

You do not decide. The tokenization algorithm (BPE here) decides from corpus statistics.

Different algorithms split in different ways. The lecture covers BPE only, as the popular one: "we can't cover all the algorithms".

Step-by-step: what determines a split recap from part 04
1
Merge rules are learned from pair frequencies in the corpus.
2
A new word is segmented by applying merges in learned order.
3
Example: "hugs" → h u g s → h ug s → hug s = 2 subwords. "bug" → b u g → b ug = 2 subwords.
number of pieces = result of the merges
Professor emphasized
  • Asked by Raj Kumar Sharma. "That is the BPE algorithm. You don't decide."
The split is an output of the algorithm and its corpus, not a manual choice.

Do all LLMs share one corpus? When are embeddings created?

[1:56:37 – 1:58:18]
The concept
  • Every LLM has a different corpus. Answers look similar for common questions because "a lot of corpus is the same" and common English tasks are easy for every model.
  • A model not trained on Hindi will not give the same answer to a Hindi query.
  • Embeddings are created while training the model, not while training the tokenizer. The tokenizer only gives vocabulary and token IDs.
  • "The corpus is never trained. The model is trained."
Intuition + layman analogy

Two students read different libraries but are both asked "what is 2 + 2". They give the same answer. Ask about a book only one of them read, and answers differ.

Justification
  • Separating tokenizer training from model training explains why one vocabulary can be reused by several models, but each model learns its own E.
shared tokenizer ≠ shared embeddings. Embeddings are specific to the trained model.
Professor emphasized
  • Asked by Ajay Kumar Prasad. "We will talk about more later."
  • OpenAI embeddings are free to use, and were already trained with their model.
"MAB" → likely embedding . "Corpus is trained" → model is trained on the corpus (as she corrects).
Corpus differs per model. Embeddings are a by-product of model training, not of tokenizer training.

[1:58:18 – 1:59:49]
The concept

Layman: "BPE adds finer-grained pieces." Technical: BPE is subword tokenization that reuses frequent character combinations instead of one token per word.

The embedding layer is trained with the LLM. OpenAI embeddings. Static vs contextual

[1:59:49 – 2:03:50]
The concept

The input embedding layer is trained inside the LLM. Nobody uses word2vec now.

ApproachStatic / contextualExamples
Skip-gram, CBOW (word2vec)Staticone vector per word, no context
Encoder-based (BERT-style)Contextualrich, sees left and right context
Decoder-based (trained LLM)Captures context while trainingOpenAI embeddings could be either, details not published
  • OpenAI's models are not available, but its embeddings are published for use via the API. They were created while training their model.
  • With such an API you give text and get a vector: the intermediate steps (tokenize, lookup, Transformer) are cut down.
  • Check the model's training corpus (English only? Thai, Hindi, Marathi, German?) before relying on its embeddings.
Scenario

Student: "Are there two kinds of embeddings: the input embedding layer, and the output embeddings after the Transformer layers?"

StageWhat you get
Embedding layer (input)Token vectors from lookup, same for the same token
After Transformer layersContext-aware vectors for each position

Professor: "I have to talk about it, that's what the remaining slides consist of." So this is deferred to module 3.

Justification
  • Learning E inside the LLM tunes the vectors to the exact task (next-token prediction) and the exact tokenizer.
  • Static word2vec vectors cannot separate senses of one word and are not trained jointly with the model.
the professor's practical rule: when you build an application with a model you must follow the same input pre-processing as in training (text → tokens → token embeddings). Hosted embedding APIs hide those steps.
Common mistakes
  • Treating an embedding API's vector as the "embedding layer" of the model. It is typically a pooled output of an embedding model .
  • Mixing static (skip-gram, CBOW) and contextual (BERT-style) embeddings.
Professor emphasized
  • Devashish Verma asked about word2vec and skip-gram. "Nobody uses word2vec now."
  • "Skip-gram and those are static algorithms. BERT-based, encoder-based algorithms are contextual embeddings."
  • OpenAI has "not published the way they trained it, but it is a contextual embedding, you can think about it".
  • Harmanpreet Singh's point: when you call an API like GPT-5, the API does the tokenization and embedding behind the scenes, so you never see these steps. Professor agrees.
"word to work" → word2vec. "what to back" → word2vec. "Germany embeddings" → German embeddings. "Maruti" → Marathi. "decoding" in "train the decoding" → decoder.
Extra reading
  • word2vec (Mikolov et al., 2013): static word vectors with CBOW and skip-gram architectures. Fetched and checked.
  • BERT (Devlin et al., 2018): deep bidirectional, contextual representations. Fetched and checked.
Input embeddings are learned with the LLM. Static methods are legacy. Hosted embedding APIs hide the whole pipeline.

"Bank" again: contextual embeddings and causal masking

[2:04:25 – 2:06:34]
The concept

Encoder-only models see the whole sentence (left and right). Decoder-only models see only the left (causal mask). So encoders give richer contextual embeddings.

Illustration of the idea the professor describes verbally (rows = query token, columns = visible token).
Step-by-step computation illustrative, 4-token sentence
1
Decoder token t can see tokens 1…t. 1 + 2 + 3 + 4 = 10 visible cells
2
Encoder token sees all n tokens. 4 × 4 = 16 cells
3
Ratio. 10 / 16 = 0.625 = 62.5 %
4
For "bank" at position 2 in "the bank was closed", decoder context = {the, bank}. Encoder context = all 4 words.
62.5 % of context visiblethe first token in a decoder sees only itself
Justification
  • For generation the future must stay hidden, since the model is predicting it.
  • A decoder-only embedding for "bank" cannot use words that come after it, which are often the clue ("bank was flooded" vs "bank approved the loan").
causal mask enables next-token generation, bidirectional attention enables richer understanding.
Professor emphasized
  • Student Ghanshyam Desai asked whether "bank" always keeps one token embedding and only the contextual embedding differs. She said he was "mixing so many concepts together".
  • "Theoretically you get contextual embeddings when you use encoder-based models. Decoder models can capture the context while training itself, but there are some limitations."
  • "I have also not gone through that detail of every model." Details of how each vendor builds embeddings are often not published. For practical work, assume the libraries give good embeddings.
"word bank" → "the word bank" (river bank vs financial bank). "Steve", "Yes, Steve" is the student acknowledging. "Lama, Quen" → Llama, Qwen.
Extra reading
  • BERT: designed for deep bidirectional representations conditioning on left and right context in all layers. Fetched and checked.
Encoder-only models see both sides. Decoder-only models see only the past, so their contextual embeddings are weaker but usable.

Misspelt words and the static vocabulary

[2:06:34 – 2:08:25]
The concept

The vocabulary is static, created in advance. Nothing in it is "wrong". It is just a set of subword units.

  • If a misspelt word like "laern" got split into pieces, the pieces are not "wrong words". They are subwords.
  • If "tasty" (or a variant) became a vocabulary entry because it was frequent in the corpus, future inputs containing it are understood as that entry.
  • No correction happens inside the tokenizer. The model interprets the pieces using what it learned.

🧠 Quick recall

1. Does BPE output embeddings?
No. BPE outputs tokens and fixed token IDs. The embedding layer in the model turns IDs into vectors.
2. When are embeddings created, and when is the tokenizer trained?
The tokenizer is trained first on the corpus (vocabulary + IDs). Embeddings are learned later while training the model.
3. Why are decoder-only embeddings less contextual than encoder-only ones?
The causal mask hides future tokens during training and use, while an encoder sees all tokens left and right.
4. For a 5-token sentence, how many token pairs are visible with a causal mask vs full attention?
Causal: 1 + 2 + 3 + 4 + 5 = 15. Full: 5 × 5 = 25. Ratio 15/25 = 60 %.
5. What will the continued pre-training assignment start from?
An open-weights model (e.g. Llama) whose training you continue. Training from scratch is not possible with course resources.
