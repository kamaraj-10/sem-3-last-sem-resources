Training a BPE tokenizer with the Hugging Face library

[1:21:20 – 1:22:29]
The concept

The course uses PyTorch and the Hugging Face implementation. BPE is already available, so you just create a tokenizer object and pass a BPE model and a BPE trainer.

Slide code (shown on screen): from tokenizers import Tokenizer, from tokenizers.models import BPE, then a BPE trainer.

Code (minimal tokenizer training) 
from tokenizers import Tokenizer
from tokenizers.models import BPE
from tokenizers.trainers import BpeTrainer
from tokenizers.pre_tokenizers import Whitespace

tok = Tokenizer(BPE(unk_token="[UNK]"))
tok.pre_tokenizer = Whitespace()                           # step 1 of BPE: split into words
trainer = BpeTrainer(vocab_size=50_000, min_frequency=2,   # the two hyperparameters from part 05
                     special_tokens=["[UNK]"])
tok.train(["corpus.txt"], trainer)                          # tokenizer training, done once
Professor emphasized
  • "We will be extensively using the Hugging Face library. Most open-source models are published on this platform."
  • How to use it will be shown in webinar 1.
"from tokenizer import tokenizer" → from tokenizers import Tokenizer. "Hugging Phase" → Hugging Face. The code block above is a typical pattern, not copied from the slide beyond lecture.
Extra reading
  • Hugging Face Tokenizers: train new vocabularies and tokenize with the Rust implementation. Fetched and checked.
You do not implement BPE yourself. A trainer object takes max vocab size and min frequency.

Which tokenizer framework should I use?

[1:22:30 – 1:24:05]
The concept

It depends on what you are trying to do.

GoalUseWhat you get
Train a new tokenizer (or extend one)Hugging Face tokenizersCustom BPE / Unigram training, normalisation and pre-tokenization rules, you choose the vocabulary size
Build an open-source model pipelineHugging Face tokenizers via the Transformers libraryLoads any Hub model's own tokenizer, chat templates, special tokens. Llama 3, Qwen3, DeepSeek, gpt-oss, Gemma
Work with OpenAI API modelsOpenAI tiktokenFast, exact token counting and API cost estimation. Encode/decode only, cannot train
Claude or GeminiVendor APINo full local library, so count tokens through their API
HF: you tokenize, then the model runs locally. API: the server tokenizes, and you use tiktoken only to count and trim.
Intuition + layman analogy

Cooking at home vs ordering food. With open-source models you own the kitchen: you choose your own knife (tokenizer). With a hosted API you only see the bill, so tiktoken is just a calculator for the bill.

Embedded-dev lens

HF is like having the vendor's SDK and source. API models are a closed binary where you can only read the byte count.

Quick cost sketch beyond lecture, assumed numbers
1
A prompt has 1,200 tokens and the reply 300 tokens (tiktoken counts the first). 1,200 + 300 = 1,500 tokens
2
Assume a price of $2 per 1M tokens. 1,500 / 1,000,000 × $2 = $0.003 per call
3
10,000 calls a day. 10,000 × $0.003 = $30 per day
$0.003 / callillustrative price, not from the lecture
Common mistakes
  • Using tiktoken to train or extend a tokenizer. It can only encode and decode.
  • Using a tokenizer from model A to feed model B. Always use the model's own tokenizer.
Professor emphasized
  • OpenAI models are hosted. tiktoken is open source and is for token counting because you pay per token on the API.
  • Claude and Gemini are proprietary: you cannot download them or extend their tokenizers.
  • "This is just a landscape of tokenizer frameworks."
"TikToken / Big Token" → tiktoken. "Cloud and Gemini" → Claude and Gemini. "Open AI uses the open models" → likely "OpenAI is a hosted service" .
Extra reading
  • openai/tiktoken: fast BPE tokeniser for OpenAI models. Fetched and checked. The README notes about 4 bytes per token on average.
Open-source models: Hugging Face tokenizers. OpenAI API: tiktoken for counting. Claude and Gemini: count via their APIs.

Tokens to token IDs at inference time

[1:24:06 – 1:25:29]
The concept

At inference the same tokenizer maps text to IDs using the fixed vocabulary built earlier.

Slide "Tokens to token IDs": "The brown dog" → [7, 0, 1]. Vocabulary from part 03: the = 7, brown = 0, dog = 1.
  • Each vocabulary word gets a fixed token ID.
  • IDs are not passed to the Transformer as they are. They are turned into token embeddings first.
Scenario

Encode "the brown dog" with the part-03 vocabulary

TokenID
brown0
dog1
the7
Step-by-step computation
1
Lowercase and split. ["the", "brown", "dog"]
2
Look up each token. the → 7, brown → 0, dog → 1
3
Result in order. [7, 0, 1]
[7, 0, 1]IDs are arbitrary labels, so a larger ID is not "more important"
Common mistakes
  • Treating token IDs as numeric features. They are just indexes. Meaning only appears after the embedding step.
Professor emphasized
  • "Remember, each word in my vocabulary will get a token ID and they are fixed."
  • "We are not passing token IDs as is" to the Transformer.
Text → fixed token IDs → (next step) embeddings. IDs alone carry no meaning.

Adding special context tokens: [UNK] and end-of-text

[1:25:31 – 1:26:43]
The concept

Besides domain words, the vocabulary gets extra helper tokens: an unknown token and an end-of-text token.

Special tokenPurpose (slide)Example ID on slide
<|unk|>New and unknown words that were not part of the training data, and so not in the vocabulary783
<|endoftext|>Separates two unrelated text sources. Prepended to each subsequent source, marking its start or end784
Every model uses its own set. Llama style differs from Mistral and others, so always use the model with its own vocabulary and tokenizer.
Intuition + layman analogy

Punctuation of the model's world. A book has chapter breaks. When many unrelated documents are glued into one training stream, <|endoftext|> is the chapter break that tells the model "forget the last story, a new one starts".

Embedded-dev lens

Like a frame delimiter or sentinel byte in a serial protocol: it frames the payload so the receiver does not mix messages.

Scenario

"The brown dog playfully chased the swift fox" with an unknown word

TokenID
the7
brown0
dog1
playfully (not in vocabulary)783 (<|unk|>)
Step-by-step computation
1
Known words map normally. the → 7, brown → 0, dog → 1
2
"playfully" is OOV, so it becomes the unknown token. → 783
3
Joining two documents with the end-of-text token. doc A + [784] + doc B
[7, 0, 1, 783, …]IDs of special tokens come after the last regular token
Justification
  • Special tokens give the model explicit markers for unknown words and for document boundaries.
  • With byte-level BPE the unknown token is rarely needed. End-of-text and chat markers remain.
more control for the designer vs more model-specific details to get right.
Common mistakes
  • Mixing tokenizers across models. Another model's special-token IDs differ, so the wrong ID can mean something else.
Professor emphasized
  • "It's very important that you use your model with its own vocabulary and its own tokenizer, because they have added their own helper tokens."
  • Complete flow: input text → same tokenizer the model was trained on → token IDs → token embeddings.
"a known token" → unknown token. "Lama" → Llama. Board: "|unk|" and "|end of text|".
Vocabulary = domain tokens + helper tokens, and the helper set is model-specific.

What is an embedding? Static vs contextual

[1:26:46 – 1:30:07]
The concept

An embedding is a vector of numbers that captures the meaning of a token. The numbers are not arbitrary.

Dimension (property)catspuppyhousesapplebaby
animal0.910.93−0.56−0.670.01
newborn−0.110.71−0.32−0.10.90
human0.190.360.310.290.87
plural0.94−0.820.94−0.51−0.11
fruit−0.51−0.91−0.50.89−0.51
Slide Figure 1-9, redrawn: a 2-D embedding space (x, y). Similar words cluster together.
Intuition + layman analogy (professor's own)

Rate every word on quality scores such as "animal", "newborn", "human", "plural", "fruit". "Cat" scores high on animal, "house" scores low. A word becomes its list of scores. Words with similar scores sit near each other on a map.

Embedded-dev lens

Think of a feature vector from a sensor: instead of one raw reading, you describe the object by many measurements, so similar objects end up near each other.

Step-by-step computation beyond lecture
1
Dot product of "cats" with "puppy" using the 5 listed dimensions. 0.91×0.93 + (−0.11)×0.71 + 0.19×0.36 + 0.94×(−0.82) + (−0.51)×(−0.91)
2
Evaluate each term. 0.8463 − 0.0781 + 0.0684 − 0.7708 + 0.4641
3
Sum. 0.8463 − 0.0781 = 0.7682; + 0.0684 = 0.8366; − 0.7708 = 0.0658; + 0.4641 = 0.5299
4
Same for "cats" with "apple". 0.91×(−0.67) + (−0.11)×(−0.1) + 0.19×0.29 + 0.94×(−0.51) + (−0.51)×0.89 = −0.6097 + 0.011 + 0.0551 − 0.4794 − 0.4539 = −1.4769
cats·puppy = 0.53cats·apple = −1.48higher dot product = more similar (here only 5 of the many dimensions)
Justification: static vs contextual (board)
  • Static embedding: one fixed vector per word, so "bank" gets the same vector whether it is a financial bank or a river bank.
  • One vector cannot separate senses. A contextual embedding changes with the sentence: bank (finance) differs from bank (river).
static is cheap and simple, contextual handles word senses but needs the whole model.
Common mistakes
  • Believing each dimension has a human-readable name. The slide says "we may oversimplify by imagining that dimensions represent concepts (they don't)".
  • Assuming the input embedding layer is contextual. See topic 8 for the precise statement.
Professor emphasized
  • Board: "Embedding ⇒ vector of numbers". These are "not just arbitrary random numbers. They capture the meaning of those words".
  • "We don't have a separate encoder model that generates the contextual embeddings" at the input of an LLM. Instead there is an embedding layer.
  • Board: "contextual embedding: bank ⇒ finance, bank ⇒ river bank".
"cat, dog, puppy" cluster is on the slide (cats, dog, puppy). "Is A contextual Embedding" → "A contextual embedding". "Pural" → plural.
Extra reading
  • word2vec (Mikolov et al., 2013): learns continuous word vectors and measures similarity. Fetched and checked.
An embedding is a meaningful vector: similar tokens are close, and contextual versions depend on the sentence.

The embedding layer and the embedding matrix E (|V| × d)

[1:30:11 – 1:31:37]
The concept

Tokenizer → token IDs → embedding layer → embeddings. The layer is a table with one row per vocabulary token.

Board: tokenizer ⇒ token IDs; token IDs ⇒ embedding layer ⇒ embeddings; E = |V| × d.
Formula / definition
E ∈ ℝ|V| × d   ·   X ∈ ℝn × d   ·   #params(E) = |V| × d
  • |V| vocabulary size (e.g. 6 in the toy example, 50,000 in practice)
  • d embedding dimension, "very important number", published by each model. Slide: BERT original = 768. Board: GPT-2 "512" (see fix note below)
  • n number of tokens in the input sequence
  • X the stacked rows chosen for the input tokens, which goes to the Transformer
Scenario

Real-scale sizes of E

Model|V|d
Llama 3 8B (slide)128,2564,096
GPT-2 small beyond lecture50,257768
Step-by-step computation
1
Llama 3 8B parameters in E. 128,256 × 4,096 = 525,336,576
2
Round. ≈ 525 M parameters (slide: "≈ 525M")
3
Share of an 8 B model. 525.3 M / 8,000 M = 0.0657 ≈ 6.6 %
4
Memory in 16-bit (2 bytes per value). 525,336,576 × 2 B ≈ 1.05 GB
5
GPT-2 small, for comparison. 50,257 × 768 = 38,597,376 ≈ 38.6 M
Llama 3 8B: |E| ≈ 525 M≈ 6.6 % of the modelbigger vocabulary and bigger d both grow E linearly
Justification: why vocabulary size matters
  • Bigger vocabulary means fewer tokens per sentence (shorter sequences).
  • Every extra token adds d parameters to E and more memory (from part 04: word-level vocabularies blow up this matrix).
sequence length vs embedding-table size.
Professor emphasized
  • "The size of the embedding matrix is vocabulary size × embedding dimensions. Every model has its own embedding dimensions."
  • "Every model will publish its embedding dimension. That is D, a very important number. And V is the vocabulary size."
She says GPT-2 is "five and two" (512) and the board says "GPT-2 ⇒ 512 dim embed", while BERT = 768. Published GPT-2 small uses 768. 512 is the dmodel of the original Transformer base model . Check the model card.
E has |V| rows and d columns. Its size is a major, model-specific memory cost.

Embedding lookup: pick rows of E to build X

[1:31:42 – 1:35:13]
The concept

The embedding layer is just a row lookup in E. E starts random and is trained along with the Transformer.

  • Same token → same vector, wherever it appears. Position is added separately (positional encoding, next topic of the course).
  • After training, E holds meaningful embedding vectors, so at inference the lookup returns correct numbers.
Intuition + layman analogy

A hotel key rack. The token ID is the room number, the embedding is the key on that hook. You just pick the key from hook number ID. Training slowly cuts better keys.

Embedded-dev lens

It is an array of structs indexed by ID: float E[V][d]; row = E[id]; with the array contents learned instead of hard-coded.

Scenario

Toy example: |V| = 6, d = 3, input "fox jumps over dog" → IDs [2, 3, 5, 1]

IDtokendim 1dim 2dim 3
0brown0.34−0.18−0.17
1dog0.921.581.30
2fox1.28−0.20−0.16
3jumps−0.400.97−1.15
4lazy−1.160.33−0.63
5over−2.84−0.78−1.41
Step-by-step computation
1
Tokenize and look up IDs. fox, jumps, over, dog → [2, 3, 5, 1]
2
Row 2 of E. [1.28, −0.20, −0.16]
3
Row 3. [−0.40, 0.97, −1.15]
4
Row 5 and row 1. [−2.84, −0.78, −1.41] and [0.92, 1.58, 1.30]
5
Stack rows in input order. X has n = 4 rows, d = 3 columns → X is 4 × 3
6
Count parameters in E. 6 × 3 = 18
7
Equivalent matrix form with a one-hot row for "fox" (ID 2). [0,0,1,0,0,0] · E = row 2 = [1.28, −0.20, −0.16]
X = 4 × 3E = 6 × 3 = 18 parametersin reality both n and d are large
Code (PyTorch) 
import torch, torch.nn as nn
emb = nn.Embedding(num_embeddings=6, embedding_dim=3)   # E: 6 x 3, random init, trainable
ids = torch.tensor([2, 3, 5, 1])                        # fox jumps over dog
X = emb(ids)                                            # row lookup
print(X.shape)                                        # torch.Size([4, 3])
Justification
  • A lookup is far cheaper than a real matrix multiplication with a one-hot vector. The results are identical.
  • Because E is a trainable parameter, the model learns the best vectors for next-token prediction.
the table is large (|V| × d) but each lookup is O(d).
Common mistakes
  • Thinking you must multiply token IDs by E. The professor first says "multiply" then corrects herself: "I'm not multiplying X into E, I am generating X". IDs are used as row indices.
  • Forgetting that E starts randomly initialised. Meaning comes only from training.
Professor emphasized
  • "In today's LLM, the embedding layer is nothing but a lookup in an embedding matrix."
  • "This embedding matrix is a trainable parameter, and at the end of the training we get the correct meaningful embedding vector for every word."
  • Board: "X = 4 × 3 matrix → Transformer".
"vocability" → vocabulary. "East" → E. "4 by 3 metrics" → 4 × 3 matrix.
Embedding layer = pick rows of a learned |V| × d table, giving an n × d matrix for the Transformer.

Q&A: token IDs, "bank" in context, dimension, other embedding types

[1:35:29 – 1:37:37]
The concept
  • Token IDs belong to the tokenizer itself.
  • "Vector + meaning = embedding?" Embeddings are vectors, nothing else. The numbers inside have somehow captured meaning.
  • How does 1-to-1 token → vector hold "bank" in a river vs finance? During training every parameter, including E, is updated, so a bit of context gets baked in. The professor says it is "not as good as encoder-only architectures", but decoders can also create contextual embeddings this way.
  • General dimension? Varies by model. BERT = 768. Check the model card.
  • "There are different types of embeddings. We can have document embeddings, …" (continues in part 07).
Justification: a precise way to say it
  • The input lookup gives the same vector for "bank" everywhere. The context-dependent vector appears after the attention layers mix information from neighbouring tokens .
the professor's answer (training updates E) explains why the base vector is a good compromise across senses. The Transformer layers do the disambiguation. Module 3 shows this.
Professor emphasized
  • Students asked: "Same token, same embedding: does it get converted to a context embedding later?" and "What is the general dimension?" She answers both.
  • Do not confuse embeddings with token IDs: IDs are part of the tokenizer, embeddings of the model.
"768 / 76, 768" → 768. "decoder training" in the answer refers to training a decoder-only LLM.
Embeddings are just vectors. Dimension is model-specific. Full contextualisation comes from the Transformer layers.

🧠 Quick recall

1. Which library for (a) training a tokenizer, (b) counting tokens for OpenAI API calls?
(a) Hugging Face tokenizers. (b) OpenAI tiktoken (encode/decode only, cannot train). For Claude and Gemini use their APIs.
2. Why are special tokens like <|endoftext|> model-specific?
Each model designer adds their own helper tokens and IDs (Llama style differs from Mistral). Use the model with its own tokenizer and vocabulary.
3. Compute the parameters in E for |V| = 32,000 and d = 4,096.
32,000 × 4,096 = 131,072,000 ≈ 131 M parameters.
4. From the toy E, what is X for input IDs [1, 0]?
Rows 1 and 0: X = [[0.92, 1.58, 1.30], [0.34, −0.18, −0.17]], shape 2 × 3.
5. Static vs contextual embedding, using "bank".
Static: one vector for "bank" always. Contextual: different vectors for bank (finance) and bank (river), depending on the sentence.
