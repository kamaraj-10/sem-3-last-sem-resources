Types of text embeddings: document, sentence, word, token

[1:37:39 – 1:38:35]
The concept

A representation model can embed different units of text. LLM input uses token embeddings.

TypeUnitTypical way to create it (professor)

Sentence embeddingone sentenceSentence Transformers (SBERT)

Token embeddingone tokenused as the input to LLMs (board)

Positional encoding: why it is needed and how it evolved

[1:38:37 – 1:41:35]
The concept

Attention has no inherent sense of order, so position information must be injected for the model to infer sequence structure.

MethodUsed inHowStatus today
Naive index (1, 2, 3, …)noneUse the raw position number"Has its own disadvantage"
SinusoidalOriginal TransformerFixed sine/cosine functions at multiple frequencies, added to the token embeddingNot used now
Learned positional embeddingsGPT-2, BERTTrainable lookup table, one vector per position, same size as the token embedding, added to itNot used now
RoPE (rotary)Llama, Qwen, DeepSeekNot added to the input. Rotates Q and K inside every attention layer, so scores depend on relative positionCurrent standard, covered in module 3
Why the Transformer needs it: shuffled words would otherwise give the same result.
Intuition + layman analogy

A bag of Scrabble tiles has the letters but not the order. Position encoding is a numbered tag stuck on each tile, so "dog bites man" and "man bites dog" can be told apart.

Embedded-dev lens

Like adding a timestamp or sequence number to each packet. Without it, an unordered network cannot reassemble the stream.

Scenario

Why token ID cannot be the position (the professor's point)

SentenceIDs from the part-03 vocabulary
"the dog … the fox"the = 7 at position 1 and position 4
Position1, 2, 3, 4 (changes along the sentence)
Step-by-step computation
1
Token ID of "the" at position 1. 7
2
Token ID of "the" at position 4. 7 (the ID is fixed by the vocabulary)
3
The positions are 1 and 4, but the IDs are identical. 7 = 7, so the ID carries no order information
4
Learned table size, GPT-2 style, for 1,024 positions and d = 768. 1,024 × 768 = 786,432 parameters beyond lecture
token ID ≠ positionID depends on vocabulary entry, position depends on order in this input
Sinusoidal encoding recap, not derived in lecture
PE(pos, 2i) = sin pos100002i/d   ·   PE(pos, 2i+1) = cos pos100002i/d
  • pos position in the sequence (0, 1, 2, …)
  • i index of the sin/cos pair (0 … d/2 − 1)
  • d embedding dimension
  • Result lies in [−1, 1]. Low i = fast oscillation, high i = slow oscillation
Worked example, d = 4 illustrative
1
pos = 1, i = 0: denominator 100000 = 1. sin(1) = 0.8415, cos(1) = 0.5403
2
pos = 1, i = 1: denominator 100002/4 = 100. sin(0.01) = 0.0100, cos(0.01) = 0.99995
3
So PE(1) = [0.8415, 0.5403, 0.0100, 1.0000] (rounded). PE(0) = [0, 1, 0, 1]
4
Add to an assumed token vector x = [0.5, −0.2, 0.1, 0.3] at position 1. [0.5+0.8415, −0.2+0.5403, 0.1+0.0100, 0.3+1.0000] = [1.3415, 0.3403, 0.1100, 1.3000]
input vector = [1.34, 0.34, 0.11, 1.30]same token at another position gets a different input vector
Justification
  • Sinusoidal: no parameters to learn and works for any length in principle.
  • Learned: flexible, but limited to the trained maximum length.
  • RoPE: models relative distance directly inside attention, which suits long contexts.
simple additive schemes (sinusoidal, learned) gave way to RoPE because relative position generalises better. The professor calls RoPE "very mathematics intensive".
Common mistakes
  • Using the token ID as position. "In any case we cannot use the token ID as my positional embedding."
  • Believing all current LLMs add a position vector to the input. Llama, Qwen and DeepSeek use RoPE inside attention instead.
Professor emphasized
  • Board (slide): numbers 1 2 3 4 5 over a sentence "going to LLM for inference" show position, and a matrix labelled "token ID / vocab" shows that IDs are fixed per vocabulary entry.
  • GPT-2 and BERT created the position embedding vector randomly and learned it during training along with the token embeddings. Its size equals the token embedding size.
  • "That is also not in use now. What is used today is RoPE. We will learn it in the third module." The older methods will not be re-taught.
"Dnn" → DNN. "ROPE" → RoPE. "GPT-2 and BERT; they changed, they learned this" → they learned position vectors.
Extra reading
  • Attention Is All You Need: introduces the sinusoidal encoding. Fetched and checked.
  • RoFormer: Rotary Position Embedding: encodes absolute position with a rotation matrix and brings in explicit relative position. Fetched and checked.
Position must be injected. Learned (GPT-2, BERT) and sinusoidal (original) add vectors. RoPE rotates Q and K in every layer and is the current standard.

Input embedding = token embedding + positional embedding

[1:41:37 – 1:42:37]
The concept

The classical input to the Transformer is token embedding + positional embedding.

xt = E[idt] + P[t]
  • E[idt] token embedding from the embedding matrix (row for token ID at position t)
  • P[t] positional embedding for position t (learned or sinusoidal)
  • xt vector that enters the first Transformer layer, same size d

Formula is a symbolic restatement of the spoken "token embedding + position embedding = input embedding". With RoPE (topic 2) the second term is not added at the input. notation added

Professor emphasized
  • A student wrote "token embedding plus word embedding". Answer: "No, it is token embedding plus positional embedding. There is nothing called word embedding" in this pipeline.
  • She then asked whether to stop for the day and unmuted the mics for questions.
Earlier (part 06) "word embedding" was used loosely. In LLM pipelines say token embedding. Static "word embeddings" (word2vec) are a different, earlier technique.
Say token embedding. Input = token embedding + position (for learned and sinusoidal schemes).

Q&A: BPE vocabulary has "meaningless" pieces. Lemmatization? Rare words

[1:43:47 – 1:46:43]
The concept
  • Question (Harmanpreet Singh): The vocabulary has single letters like b, g, h, n, p, s, u that mean nothing. Is there a lemmatization or filtering step afterwards?
  • Answer: No. Those pieces do have a use, because they allow rare words to be built.
Scenario

The rare word "taaaaasty" under two different vocabularies

CasePiecesTokens
Corpus has seen many a's: "aaa" existst | aaa | a | a | sty (similar splits possible)≈ 3–5
Corpus rarely has repeated at | a | a | a | a | a | sty7
Step-by-step computation
1
"tasty" with five a's has 1 t + 5 a's + "sty". 1 + 5 + (s,t,y as one piece "sty") = 7 pieces in the worst case
2
If "sty" exists as one token. t, a, a, a, a, a, sty = 7 tokens
3
If "ta" and "aa" merges exist. fewer tokens (e.g. t | aa | aa | a | sty = 5), still no [UNK]
no [UNK]more rare = more tokens, never a failure (if the base characters exist)
Justification
  • Single characters are the fallback pieces. Without them rare words would hit [UNK].
  • This is also why modern chat models cope with spelling mistakes: tokenization is one of the reasons (the professor adds that "obviously there are other things also").
rare or misspelt words cost more tokens, but the model still receives something it can interpret.
Professor emphasized
  • "Nowadays you write anything, we write so fast in Claude or ChatGPT, we misspell, but it still understands. One of the criteria is this tokenization process."
  • Social-media text with unusual spellings is where this matters.
"limitization" → lemmatization. "cloud or charge" → Claude or ChatGPT. "Non. No, no." is the answer "No".
Single-character pieces are not noise. They are the safety net that makes rare words and typos representable.

Q&A: when do I care about byte- or character-level tokenization?

[1:46:43 – 1:48:25]
The concept

If you build an application on an existing LLM, you do not train the tokenizer. The LLM builder already did.

  • Tokenizer design matters only when you train your own tokenizer and your own model.
  • LLMs are designed to be used in many applications, so their builders take care of the tokenizer from the start.
  • If an LLM used a tokenizer unsuitable for, say, social media text, that is the LLM builder's problem, not the application designer's worry.
Intuition + layman analogy

Driving a car vs designing the engine. The driver uses the engine and does not redesign it. Tokenizer design is the engine work, done by model builders.

Professor emphasized
  • "As an application designer, you don't have to do all these things."
  • Harmanpreet: "So it's universal." Answered by the above.
"Anurag" is the name used to thank the student, not a transcript fix.
Justification
  • Application designers can focus on prompts, data and evaluation.
  • You inherit the tokenizer's weaknesses, such as poor handling of your language, and may pay more per request in tokens .
convenience of reuse vs control. Own tokenizer only if you train your own model.
Application designers pick a model and use its tokenizer. Tokenizer design matters when you train a model from scratch.

Q&A: tokens → token IDs → embeddings. Are embeddings precomputed?

[1:48:25 – 1:53:01]
The concept

Three representations of the same input, one after another (board drawn on slide).

Board on the "Tokenization" slide. Each token → one ID → one column vector.
  • Token IDs are assigned to every vocabulary word at tokenizer-training time, once.
  • At inference the prompt is tokenized with the same tokenizer, and IDs are read from that fixed table.
  • Embeddings are not pre-generated and stored per word for the prompt. The embedding layer produces vectors for the tokens actually present in the input.
Scenario

Student's picture vs the professor's correction

ViewStatement
Student"We have a 50 × 10 matrix already created. At inference we just retrieve the rows by token ID."
ProfessorYes during training the matrix is learned. At inference only the words in the input are processed by the Transformer.
Step-by-step computation
1
Learned table for a 50-word vocabulary and d = 10. 50 × 10 = 500 numbers (exists after training)
2
Prompt with 4 tokens. 4 IDs → 4 rows picked
3
Only these enter the Transformer. 4 × 10 = 40 numbers, not 500
4
Real scale, 50,000 × 768. 38.4 M stored, but a 4-token prompt uses 4 × 768 = 3,072 values
only n rows used per promptweights are fixed after training. They are "looked up", not "generated"
Common mistakes
  • Thinking each vocabulary word has a stored "meaning vector" independent of training. It is only meaningful after training.
  • Reading the slide diagram too literally. The professor said the figure (from a book, "JLMR" in the transcript) "is a little bit misleading", because it shows 50,000 embeddings drawn next to the 50,000-entry vocabulary.
  • Saying "word embedding" for the LLM input. Use token embedding.
Professor emphasized
  • "When you use the model, you have to use the same tokenizer with which the model is trained on."
  • "Do not use word embedding, use token embeddings."
  • "During training, yes. But during inferencing, only the tokens in your input get processed by the Transformer."
  • Chat questions (visible on screen) asked: "For 'mug', u,g is there but not m, can you explain?" and "What is the use of token ID?"
"JLMR" → probably the book Hands-On Large Language Models (Figure 3-5 style) . "BOLLIGORLA SHEKAR: this token is randomly generated" refers to the initial random values of E. "Search" in the transcript is background noise.
IDs come from the fixed tokenizer vocabulary. Embedding vectors come from the learned embedding matrix, and only the input tokens' rows are used.

🧠 Quick recall

1. Why can the token ID not be used as positional information?
The ID is fixed per vocabulary entry. The same word at positions 1 and 4 has the same ID, so IDs cannot encode order.
2. Name the three position schemes and one model family for each.
Sinusoidal (original Transformer), learned embeddings (GPT-2, BERT), RoPE (Llama, Qwen, DeepSeek).
3. Compute PE(1) for d = 4 with the sinusoidal formula (2 decimals).
[sin 1, cos 1, sin 0.01, cos 0.01] = [0.84, 0.54, 0.01, 1.00].
4. Which is correct for the LLM input: "token + word embedding" or "token + positional embedding"?
Token embedding + positional embedding (for learned/sinusoidal). There is no "word embedding" in this pipeline. With RoPE, position is applied inside attention instead.
5. In what order do corpus, tokenizer training and model training happen?
Build corpus → train tokenizer (vocabulary and merges) → tokenize the corpus → train the model.
