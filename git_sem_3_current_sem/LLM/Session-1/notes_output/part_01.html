[00:03 – 02:25]
The concept

Check Takshila announcements. Mics stay muted for now. Ask in chat.

Module map: what each module covers and why this order

[04:53 – 09:03]
The concept
#ModuleTopics (from handout)Time

2LLM pre-training and fine-tuningPre-training, data, scaling laws, domain adaptation, frontier-model details, types of fine-tuning, SFT, PEFT~3 h

7Prompt engineering and reasoningStructured and iterative reasoning, prompt as system design, structured data, test-time compute scaling, context engineering~4 h
Mid-semester syllabus = modules 1 to 5. From module 6 onwards it is end-semester only.
Intuition + layman analogy

The course is like learning to run a restaurant. First how food is made (modules 1–3), then how to serve it fast and cheaply (4–5), then training the taste of the chef (6), then writing a good order slip (7). Building the kitchen from scratch needs huge resources, so most of the course is about using LLMs effectively.

Justification: why pre-training and fine-tuning are in module 2
  • Assignment 1 is based on continued pre-training and fine-tuning. The webinars and labs also depend on module 2, so it is taught early.
  • Module 3 asks you to review attention and the Transformer from the first-semester DNN course before the session starts, so that class time goes to doubts.
  • Inference comes before optimisation because you first need to see how an LLM is used, then where it is slow.
  • Not everyone can build an LLM from scratch (massive resources), so training-side content is limited to what you can do on a modest GPU budget.
depth on architecture versus time for hands-on work: the labs and webinars carry the hands-on part.
Professor emphasized
  • "Please review attention and Transformer from your DNN class by the time we start the third session."
  • Module 3 will show how current LLM architecture (2024–2026 frontier models) has changed from the vanilla Transformer.
  • Module 6 will cover RLHF techniques such as PPO and DPO in detail.
"RL HF" → RLHF. "BPO" → DPO (Direct Preference Optimization, as in the handout). "Dnn" → DNN.
Modules 1–5 (foundations, training, architecture, inference, optimisation) form the mid-sem syllabus. Review attention and Transformer before module 3.

Modules 8 and 9 were reshaped to avoid duplicating another course. The focus is the LLM design perspective, not the application pipeline.
Scenario

What is, and is not, taught in module 8 (RAG)

Will be taught

RAG pipeline overview so you can build one; how LLM design changes for RAG; Self-RAG; how industry implements self-correcting RAG in the application layer.

Will NOT be taught in detail

Chunking strategies; dense and sparse retrieval mechanisms. These are covered in the other course.

Justification
  • "You will learn something from every course you take." No repeated content across courses.
The same applies to agents: module 9 gives the introduction, then focuses on agent memory, the context/memory problem and how LLM architectures evolved to meet agentic requirements.
Professor emphasized
  • Evaluation: classical metrics are known from ML and DL, so the lecture adds the model vs system distinction.
  • Safety and security: popular attacks, defence mechanisms and safety aspects.
  • Application demos will be shown in the agent module.
"JANU AI" → GenAI. "self-reg" → Self-RAG. "Llms Agents" → LLM as Agents (handout title).
Modules 8–11 are two-hour modules on RAG (LLM view), agents, evaluation and safety, with RAG basics left to the other course.

Evaluation scheme and assignments

[12:29 – 15:00]
The concept

No quizzes. Two group assignments, a closed-book mid-sem, an open-book end-sem.

Marks arithmetic
Total = A1 + A2 + Mid + End
  • A1 Assignment 1 marks = 15 (continued pre-training / fine-tuning theme)
  • A2 Assignment 2 marks = 20
  • Mid mid-semester exam = 30 %, closed book
  • End end-semester exam = 35 %, open book
Step-by-step computation
1
Assignment total. 15 + 20 = 35
2
Add the exams. 35 + 30 + 35 = 100
3
Share of coursework vs exams. assignments 35 % ; exams 30 + 35 = 65 %
Total = 100 %65 % of the grade comes from the two exams
Assignment rules
ItemRule
FormatGroup assignment, group size 4 (standard)
Topics2 problem statements for A1 and 2 for A2, 4 in total. Choose via Google Form on Takshila
No choice givenRandom assignment, balanced across groups
DataOne training corpus / dataset is cleaned in A1 and may be carried into A2
QuizzesNone (written on the board)
DatesPosted in announcements after about one week, when registrations close
Justification
  • Assignments are "like a mini project". Taking them seriously gives hands-on experience and good marks.
  • Dates are announced after registrations close so late registrants do not miss e-mails.
more freedom (choose a topic matching your work) against the need to balance load, so unchosen topics are assigned randomly.
Common mistakes
  • Treating the open-book end-sem as easy. Open book rewards understanding, not lookup.
  • Waiting for an e-mail about deadlines. Check Takshila announcements.
Professor emphasized
  • Think early about whom you want in your group of four, since "by now you know your colleagues well".
  • The lead facilitator will share the group Google Form together with the problem statements.
  • Webinar schedule and assignment deadlines come as a centralised calendar in announcements.
"Ass-1 ⇒ 15, Ass-2 ⇒ 20" on the board. "my lead LF" → lead lab facilitator .
35 % assignments (15 + 20, groups of 4, no quizzes) + 30 % closed-book mid-sem + 35 % open-book end-sem = 100 %.

BITS remote GPU lab (Prayogshala + Kubeflow)

[15:00 – 18:15]
The concept

A remote lab on BITS hardware. Front end: Prayogshala. Back end: Kubeflow. You pick the GPU when you create a notebook server or pod.

GPUVRAM (board)
NVIDIA L40S40 GB
NVIDIA A10080 GB
RTX 600096 GB
23 GPU cards in total, installed at the Hyderabad campus. Other courses use AWS or RunPod back ends, this one does not.
Intuition + layman analogy

It is a shared university workshop: powerful machines are there, but everyone must book a slot. If the whole batch turns up on the last three days before the deadline, there is a queue.

Embedded-dev lens

Like a shared lab bench with a few oscilloscopes. Book early, release when done.

What fits? A quick sizing check beyond lecture
1
Weights of a 7 B-parameter model in 16-bit (2 bytes each). 7×109 × 2 B = 14×109 B ≈ 14 GB
2
Compare with the smallest card. 14 GB < 40 GB (L40S)
3
Training needs extra memory for gradients, optimizer state and activations, so plan for several times the weight size.
7 B model weights ≈ 14 GBillustrative, not stated in the lecture
Common mistakes
  • Starting GPU work in the last three days. Everyone competes for the same cards.
  • Skipping the manual. "If you follow thoroughly those steps you will not find any issues."
  • Leaving a GPU session running when idle, which blocks other students.
Professor emphasized
  • A detailed access manual will be shared. Setup is "a one-time effort of half an hour".
  • Webinar 1 demonstrates the lab from the start.
  • You will experiment with open-source models that fit these GPUs.
  • "Use this responsibly" so that others can use it too.
"Prayog Shala" → Prayogshala. "key flow" → Kubeflow. "800" → A100 (board). "L40s. Six" → L40S. "RTS 6000" → RTX 6000. "I guess" figures for VRAM are as written on the board.
Use the BITS remote GPU lab through Prayogshala (Kubeflow back end), start early and release resources when done.
