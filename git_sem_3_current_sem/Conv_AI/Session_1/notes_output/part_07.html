The concept

User: "What's my account balance and recent transactions?"

Intuition + layman analogy (professor's)

"This is like our C programming function calling." The agent sees get_balance(user_id) and get_transactions(user_id, limit) as function prototypes in a header. The LLM decides which to call and in what order. You only provide the prototypes and their implementations.

  • Logging full account numbers or names while debugging. That breaks the safety stage.

  • Memory and safety "happen at every stage, not in sequential order".
  • "We give the list of tools; the agent decides when to call: get_balance first, then get_transactions, and so on."
  • Banking was chosen because "everyone knows the banking process; it's a very local example."

Q&A: where is the feedback loop? Human-in-the-loop and observability

[1:41:42 – 1:46:22]
The concept

Three different "feedback" ideas, which got mixed up in class and were then clarified

Kind of feedbackWhereWho
Observation inside the agentTool invocation → back to reasoning (3 ⇄ 4)The agent itself checks tool results and redoes the step if wrong
End-user sees the resultStage 7, responseThe person who made the request
Evaluation (observability, HITL, LLM-in-the-loop)Every intermediate output, at every timestampHuman reviewers or a judge LLM. This is an evaluation design strategy.
Intuition + layman analogy

A chef tastes the soup while cooking (observation). The diner eats it (end-user response). A food inspector with cameras in the kitchen checks every step, temperatures and times (observability, HITL or LLM-as-judge evaluation).

Embedded-dev lens

Observation ≈ checking a return code and retrying. Observability ≈ tracing with a logic analyser or ETM trace on every bus transaction. HITL ≈ a manual test bench sign-off.

Justification
  • Traditional software uses deterministic pass/fail tests. Agents need observability metrics on intermediate outputs, because the path can change on every run.
  • Learning a user's preference (Air India vs IndiGo) from wrong bookings is a memory-plus-evaluation design problem. It is covered later.
Common mistakes
  • Confusing human-in-the-loop (an evaluation or approval strategy) with the end user simply seeing the response.
Professor emphasized
  • "Observation will happen here [after tool invocation]. This will be detailed in further classes."
  • "HITL is used as an evaluation strategy." "We can use human in the loop or LLMs in the loop, and measure all intermediate outputs at every timestamp."
  • "There are so many frameworks available to do this."
"Observability matrix" → observability metrics. "HIL" → HITL (human-in-the-loop).
the agent self-corrects through observation, the user sees the response, and the engineers evaluate everything through observability with human or LLM judges.

Production concerns for conversational AI

[1:46:22 – 1:47:40]
The concept

"Working in development is not enough: agents must work reliably at scale."

📊 Observability: what to track

  • Conversation flows
  • Tool invocations
  • Token usage per conversation
  • Response latencies and error traces

Tools: LangSmith, Arize Phoenix, OpenTelemetry

💰 Cost management

  • Prompt caching (up to 90% lower input cost)
  • Model routing (smaller models when appropriate)
  • Token budgets per user/session
  • Efficient retrieval (smaller context)

Example: customer support ≈ $0.02–0.10 per conversation

⚡ Latency budgets

  • Chat responses < 2 s
  • Tool execution < 5 s
  • Complex reasoning < 30 s
  • Set expectations with progress indicators

🛡 Safety & security: defence layers

  • Input validation (prompt-injection defence)
  • PII detection and redaction
  • Output filtering (toxicity, hallucinations)
  • Human-in-the-loop for critical actions

Principle: never rely on a single safety layer.

Intuition + layman analogy

Running a restaurant chain, not a home kitchen. You need CCTV and order logs (observability), a food-cost budget and bulk buying (cost and caching), a service time limit per table (latency), and food-safety checks at delivery, kitchen and storage (layered safety).

Formula

Per-conversation input cost with prompt caching

C = Tcached · p · (1 − d) + Tnew · p106
  • C input cost per conversation ($)
  • Tcached tokens served from the cache (e.g. a long, fixed system prompt)
  • Tnew uncached input tokens
  • p price per million input tokens ($ / 1M)
  • d cache discount (0–1). The slide quotes "up to 90%", so d ≤ 0.9.

Justification
  • Caching helps most when a large, fixed prefix repeats on every call (system prompt, tool schemas).
  • Model routing sends easy queries to small, cheap models and keeps the big model for hard ones.
  • Layered safety: if prompt-injection defence misses something, output filtering or HITL can still catch it.
cost vs latency vs quality vs safety. Every extra safety layer or reasoning step adds latency and tokens.
Common mistakes
  • Reading "up to 90% lower input cost" as a 90% total saving. It applies only to the cached tokens, and output tokens are unaffected.
  • Relying on a single guardrail. The slide principle is "never rely on a single safety layer".
Professor emphasized
  • Answering the flight-booking feedback question: track conversation flows, tool invocations, tokens per conversation and latency. "This is a separate area … there is a long way to go to come to this level."
Extra reading
  • OpenTelemetry – What is OpenTelemetry?: vendor-neutral traces, metrics and logs.
  • Arize Phoenix: open-source LLM tracing and evaluation.
  • Anthropic – Prompt caching docs
  • OWASP Top 10 for LLMs (2025): LLM01 prompt injection, LLM02 sensitive info, LLM10 unbounded consumption (cost).
production = observability + cost control + latency budgets + layered safety. Each needs deliberate design.

From demo to reliable production

[1:47:40 – 1:53:58]
The concept

Old mindset: "My chatbot works!"

  • Simple response, chat replies
  • Low complexity
  • Binary success: it replies

New mindset: "My agent works correctly, repeatedly, under all conditions"

  • Correctness: accurate data
  • Consistency: reliable performance
  • Repeatability: consistent output
  • Robustness: handles edge cases
"AI is no longer judged by intelligence, but by reliability."
Intuition + layman analogy

A car that starts once in the showroom is a demo. A car that starts every morning for 10 years, in rain and at 45 °C, is a product. Automotive-grade software is judged the same way: not "does it boot" but "does it behave correctly under every corner case".

Formula (beyond lecture)

Why every step needs a checkpoint: reliability compounds

Rtask = n∏i=1 ri   (= rn if all steps are equal)
  • Rtask probability the whole multi-step task succeeds (0–1)
  • ri success probability of step i (tool call, reasoning step), assuming independent steps
  • n number of steps in the agent's plan
Scenario

A 5-step agent where each step is 98% reliable illustrative

n5

2

3

4
0.98⁵ = 0.922368 × 0.98 = 0.903921
R_task ≈ 90.4 %so about 1 in 10 tasks fails even though each step is "98% good"
Justification
  • Compounding explains the professor's "everywhere we have to put a gate and check": checkpoints catch errors before they spread.
  • Judicious use: "Using an AI agent for every task is foolishness". Every call costs money, and fewer steps also means higher reliability.
  • "No system is perfect. We cannot expect 100%." Design for failure handling.
agent power (more steps and tools) vs reliability and cost (fewer steps). Use the simplest design that meets the goal.
Common mistakes
  • Treating "it replied" as success. That is the old mindset.
  • Reaching for an agent (or even an LLM) for every task. Use them only where they add value.
  • Thinking the LLM is "magic": "if you give some input, the LLM will give whatever we want. No, definitely not."
Professor emphasized
  • Board: "What strategy?" How reliably an agent calls the right tools "is in our hands". The course covers this "to some extent".
  • What memory should store vs not store: covered in Session 3 or 4. Proprietary models each have their own algorithms.
  • Watch how ChatGPT (2022–2026) and the Claude model families keep evolving. Each new requirement brings new failures to overcome. "It is not a switch-on button."
  • The banking agent is a hypothetical study. No real banking agent like this exists yet.
"pits and falls" → pitfalls. "Sonnet or Haiku or a Fable" → Claude model families Sonnet, Haiku, Opus . "Danger" / "Damn!" are mis-heard interjections (likely "Exactly").
Extra reading
  • Anthropic – Building effective agents: "Success … isn't about building the most sophisticated system. It's about building the right system", and "the autonomous nature of agents means higher costs, and the potential for compounding errors."
a production agent is judged by correctness, consistency, repeatability and robustness. Small per-step errors compound, so add checkpoints and use agents only where they add value.

🧠 Quick recall

1. In the banking example, which tools are called and what does the safety stage check?
get_balance(user_id) and get_transactions(user_id, limit=5). Safety checks that the data belongs to the correct user, that no PII appears in logs, and that the response contains only authorised info.
2. What are the four latency budgets and four defence layers on the slide?
Latency: chat < 2 s, tool < 5 s, complex reasoning < 30 s, plus progress indicators. Defence: input validation, PII redaction, output filtering, HITL for critical actions.
3. 2,000 input tokens, 1,500 cached, p = $2/M, d = 0.9. What is the input cost per conversation?
Cached: 1,500 × 2 × 0.1 / 10⁶ = $0.0003. New: 500 × 2 / 10⁶ = $0.0010. Total = $0.0013 (vs $0.0040 without caching, a 67.5% saving).
4. What is the success rate of a 3-step plan with 95% per-step reliability?
0.95³ = 0.9025 × 0.95 = 0.857375 ≈ 85.7%.
5. Name the four properties of the "new mindset".
Correctness, consistency, repeatability, robustness. "AI is judged by reliability, not intelligence."
