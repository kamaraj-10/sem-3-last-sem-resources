Agent lifecycle: each stage in depth

[1:22:24 – 1:28:00]
The concept

The agent's objective is to complete the task it was given. It loops, re-plans and retries until done.

#StageWhat happens (as explained in class)
1RequestReceive input, validate and sanitize (is the request allowed and ethical?), extract entities and intent.
2RoutingClassify intent, select the tool from the given set, or route to a sub-agent (multi-agent). A single agent does its own routing.
3ReasoningBreak the goal into steps, notice missing information, plan which tool calls to make. Only planning happens here.
4Tool invocationActually call the planned APIs, query databases, execute code. Then go back to reasoning to check whether the answer is sufficient.
5MemoryStore conversation history and important entities, maintain session state, update preferences. Not a sequential step.
6SafetyBlock toxic content, check facts, redact PII. Sanitisation check on the input and the output. Not a sequential step.
7ResponseGenerate the reply, format it for the channel, deliver.
Know what each stage owns, and which stages are sequential (1–4, 7) vs cross-cutting (5, 6).
Intuition + layman analogy

A bank teller. They check your ID and refuse "tell me my colleague's balance" (request validation). They decide whether you need loans or deposits (routing), work out the steps (reasoning), use the core-banking system (tool invocation), and update your file the whole time (memory). Throughout, they follow privacy rules and never read out someone's PAN number (safety).

Embedded-dev lens

Request validation ≈ checking packet CRC and length before parsing. Safety ≈ an MPU/MMU guarding every access, not a single step. Memory ≈ a global state struct read and written by every task.

Justification
  • Validating at the request stage stops misuse early, e.g. an HR bot must not reveal a colleague's leave balance.
  • Splitting reasoning (plan) from tool invocation (do) lets the agent re-plan when a tool fails, without redoing everything.
  • Making memory and safety cross-cutting means preferences are captured and PII is guarded wherever it shows up.
Common mistakes
  • Putting safety only at the end. The professor stressed a sanitisation check at the input and at the output.
  • Thinking routing always means multi-agent. A single agent still routes, by selecting tools.
Professor emphasized
  • "If the plan is not good, it will come back and do the re-planning."
  • "You cannot bluff the bot": you can't ask the HR bot how many leaves a colleague has. Validation "happens in many directions".
  • "We always have to build a responsible AI." PII = personally identifiable information.
  • "If the user sets 5 iterations it will try up to five times. If it gets a good result the first time, it stops there."
"what my colleague Pierre is having" → what my colleague / peer has. "it will tie for" → it will try. "Guard rights information" → likely "guard the information" .
stages 1–4 and 7 carry the task forward. Memory (5) and safety (6) wrap every stage. Re-planning and retries happen inside the 3 ⇄ 4 loop.

Case study: "Book me a flight from Bangalore to Chennai next Friday under ₹8,000"

[1:28:00 – 1:36:56]
The concept

An agent must do the task (book), not just describe how to do it

Board: "do a task". If you ask ChatGPT or Claude chat "book me a flight", it lists flights and suggests portals but does not book. An agent with the right tools goes on to booking and payment.

Trace a real request through all lifecycle stages and identify the entities, tools, reasoning steps and stopping condition.
Intuition + layman analogy

A travel agent vs a travel brochure. The brochure (chatbot) lists options. The travel agent (AI agent) checks fares, remembers that you prefer IndiGo, picks the flight, books it and gives you the ticket. You only hand the agent your card if you trust them, which is the autonomy question.

Step-by-step through the lifecycle
1
Request: validate it (legitimate booking, user authenticated). Extract intent = book_flight and the entities above.
2
Routing: from the given tool set, pick the travel-booking tools.
3
Reasoning: the plan is (a) list all flights on Fri 30 Oct, (b) filter fare < 8,000, (c) apply the stored preference, (d) choose, (e) book, (f) pay. Gap: time not given, so ask the user or assume any time.
4
Tool call: search returns 5 flights.
5
Reasoning (observe): apply the "under ₹8,000" filter.
7,450 < 8,000 ✔ · 8,900 ✘ · 6,980 ✔ · 8,050 ✘ · 7,999 ✔ → 3 flights
6
Memory: preferred airline IndiGo, so keep 6E-101 (7,450) and 6E-555 (7,999). Choose the cheaper one.
min(7,450, 7,999) = 7,450 → 6E-101
7
Headroom against the budget. 8,000 − 7,450 = ₹550 under budget
8
Tool call: booking API, then safety and autonomy gate: payment needs user confirmation (no full financial autonomy).
9
Stop condition: the goal "flight booked" is met (or the iteration limit is reached). Response: confirmation in text, voice or UI.
Book 6E-101 · 06:10 · ₹7,450₹550 under budget
Without memory the cheapest valid option would be QP-1342 at ₹6,980. Memory changes the decision. "Under ₹8,000" is strict, so ₹8,050 fails while ₹7,999 passes.
Justification

When does the agent stop reasoning? (student question)

  • It loops until the goal is met (the booking is confirmed) or the iteration limit is hit. This is the ReAct loop.
  • The LLM plans "the same way we would": list, filter, choose, book. That is why reasoning ability matters.
  • If you hard-code "call search, then filter, then book", it becomes a workflow, not an agent.
  • Payment: "no one has given full autonomy to do financial transactions". The tools and APIs you grant define what the agent can do.
full autonomy (convenient but risky with money) vs a human approval gate (safe but slower). Today, payments sit behind a gate.
Code (tool definitions given to the agent, JSON-style) 
tools = [
  {"name": "search_flights",

flights = [("6E-101", 7450), ("AI-503", 8900), ("QP-1342", 6980), ("UK-829", 8050), ("6E-555", 7999)]
ok = [f for f in flights if f[1] < 8000 and f[0].startswith("6E")]
print(min(ok, key=lambda f: f[1]))           # ('6E-101', 7450)
Common mistakes
  • Missing the time and budget entities. Students named date and time. The professor added budget.
  • Treating "list flights" as completing "book me a flight". The intent is to book.
  • Hard-coding the tool order, which turns the agent into a workflow.
Professor emphasized
  • "Chatbots will tell you how to do. Here, do a task. That's the difference."
  • Tavily is a very good, free web-search API, and it will be used in the course (Lab 1).
  • Frameworks to be studied: LangGraph, Google ADK, CrewAI.
  • Level of autonomy: "We are going to take a call on that. Given the list of tools and APIs, that is in our hands."

Lifecycle flow: only stages 3 and 4 loop. Memory and safety are cross-cutting.

[1:36:56 – 1:37:58]
The concept
Intuition + layman analogy

"What is 2 + 2?" goes straight to the counter for an answer, with no need to call anyone. "Book my flight" goes into the back office loop. CCTV (safety) and the customer file (memory) are active everywhere in the building.

Common mistakes
  • Drawing memory and safety as boxes 5 and 6 after tool invocation. They are horizontal bars under all stages.
Professor emphasized
  • "Memory and safety will come at every point." "Only stages 3 and 4 form a loop. A simple question can skip the tools." "It's a numbering, not a definite cycle."
Request → routing → [reasoning ⇄ tools]* → response. Memory and safety run underneath every stage.

🧠 Quick recall

1. Which stage does the planning and which does the actual API call?
Reasoning (3) plans. Tool invocation (4) executes. Then control returns to reasoning to check the result.
2. List the entities in "Book me a flight from Bangalore to Chennai next Friday under ₹8,000".
Source = Bangalore, destination = Chennai, date = next Friday, time (missing, so ask), budget = < ₹8,000.
3. Fares 7,200 / 8,000 / 7,950 / 8,400 with "under ₹8,000". How many qualify and which is cheapest?
7,200 and 7,950 qualify (8,000 is not under 8,000), so 2 flights. The cheapest is ₹7,200.
4. When does the agent's reasoning loop stop?
When the goal is met (e.g. booking confirmed), or when the iteration limit is reached.
5. Why don't agents pay for the flight autonomously today?
Level of autonomy: no one has given agents full autonomy over financial transactions. Payments go behind human approval, and the tools and APIs granted define what the agent can do.
