Exercise: map the agent lifecycle

[1:53:58 – 1:55:00]
The concept

"Find me a good Italian restaurant near my office that's open tonight and make a reservation for 2 at 7 PM"

The first half ("find me…") is an ordinary LLM / ChatGPT task. The second half ("make a reservation") needs an AI agent, because only an agent with autonomy and tools can do a task. Board: "AI agent → do a task".

For each of the 7 stages, answer the question on the slide.
Intuition + layman analogy

Asking a friend "which Italian place is good near my office?" gets you advice. Asking your personal assistant to "book it for 2 at 7" gets you a confirmed table.

Scenario

Candidate restaurants returned by a places API illustrative data + suggested answer (not solved in class)

RestaurantRatingDistance from officeOpen tonightTable for 2 at 7 PM
Trattoria Roma4.61.2 kmYesYes
Pasta Street4.20.5 kmYesYes
Little Italy4.83.5 kmYesNo
Bella Napoli4.50.8 kmNon/a

Assumed thresholds: "good" = rating ≥ 4.5, "near" = ≤ 2 km. In practice the agent would ask the user or use stored preferences.

Step-by-step: filling in the slide's table
1
Request: entities are cuisine = Italian, quality = good, location = near office (resolve from the user profile), time = tonight, party = 2, slot = 7 PM. Validate that the user is authenticated.
2
Routing: tools = places/maps search, reviews/ratings, reservation API (or a booking sub-agent).
3
Reasoning: resolve the office location → search Italian restaurants → filter (good, near, open tonight) → check the 7 PM slot → reserve → confirm.
4
Tool invocation and filtering:
Pasta Street: 4.2 < 4.5 ✘ · Little Italy: 3.5 km > 2 ✘ · Bella Napoli: closed ✘ · Trattoria Roma: 4.6 ✔ 1.2 km ✔ open ✔ slot ✔
Then call reserve(restaurant="Trattoria Roma", party=2, time="19:00").
5
Memory: store office location, cuisine preference (Italian), usual party size, booking id.
6
Safety: confirm before committing (date, time, party size), share no PII with the restaurant beyond name and phone, and no payment without approval.
7
Response: "Booked Trattoria Roma (4.6★, 1.2 km) for 2 at 7 PM tonight. Booking ID …"
Trattoria Roma · 2 people · 7 PM1 of 4 candidates passes all filters
Justification
  • Only one candidate meets every constraint. The highest rated (Little Italy) fails on distance and availability, which shows why the agent must check all constraints rather than just ranking by rating.
Professor emphasized
  • "This is where the question makes clear the need for an AI agent. Only an agent can do a task."
  • "This is all a hypothetical study … Testing, observability, building a reliable system is again a big study."
"find" is LLM work, "reserve" is agent work. Mapping a request onto the 7 stages exposes the entities, tools, plan, memory and safety checks it needs.

Formula (rule of thumb)

Will the model fit on the GPU?

Mweights ≈ Nparams × b
  • Mweights memory for the weights alone (bytes). The KV cache and activations need extra memory on top.
  • Nparams number of parameters (Qwen2.5-1.5B-Instruct: 1.54 B, from the model card)
  • b bytes per parameter: 2 for BF16/FP16, 1 for 8-bit, 0.5 for 4-bit
Step-by-step computation
1
BF16. 1.54 × 10⁹ × 2 B = 3.08 × 10⁹ B ≈ 3.08 GB
2
4-bit quantised. 1.54 × 10⁹ × 0.5 B = 0.77 GB
3
Compare with the T4's 16 GB of VRAM . 3.08 / 16 ≈ 19 % used by weights
≈ 3.1 GB, fits easily on a free T4a 70 B model at BF16 would need ≈ 140 GB, which is lab territory

Weather agent: the five stages in the notebook

[1:58:12 – 2:01:54]
The concept
StageWhat happens
1 BaselineLLM without tools: observe its limits
2 Tool definitionDefine the weather function schema (JSON)
3 Tool selectionThe LLM decides when to use the tool. It replies with a <tool_call> instead of plain text. Nothing is executed yet.
4 ExecutionCall the actual weather API (Open-Meteo: free, no key)
5 Response generationThe LLM turns the tool result into a natural-language answer
Intuition + layman analogy

The model is a manager who can only write memos. It writes "please call get_weather for Mumbai" on a slip (<tool_call>). Your Python code is the secretary who reads the slip, makes the call and hands back the result. The manager then writes the reply.

Embedded-dev lens

Like an RPC stub: the model emits a serialised request (JSON), your dispatcher parses it with json.loads, validates it, invokes the handler and returns the result. A bad frame (invalid JSON) is dropped, which is the except JSONDecodeError: pass in the notebook.

Scenario (observed in class)
RunObserved output
Stage 1, no toolsQwen declined ("I'm sorry, I cannot answer…") and drifted into unrelated content about India and culture. That is hallucination or deflection, not grounded in real-time data.
Stages 2–5, with toolTool result: country India, temperature_c 36.4, condition "Clear sky", humidity_percent 32, humidity_level "Low (dry)". Reply: "Current weather in Mumbai is Clear sky with a temperature of 36.4 °C. The humidity level is Low (dry)…"
Code (condensed reconstruction of the notebook's key cells) 
import json, re, requests

SYSTEM = "You are a weather information agent. Use the get_weather tool for any weather question."
tools = [{"type": "function", "function": {
    "name": "get_weather",
    "description": "Current weather for a city",
    "parameters": {"type": "object",
                   "properties": {"city": {"type": "string"}},
                   "required": ["city"]}}}]

def parse_tool_calls(text):
    calls = []
    for block in re.findall(r"<tool_call>(.*?)</tool_call>", text, flags=re.DOTALL):
        try: calls.append(json.loads(block.strip()))
        except json.JSONDecodeError: pass
    return calls

def get_weather(city):                                   # Open-Meteo: free, no API key
    g = requests.get("https://geocoding-api.open-meteo.com/v1/search",
                     params={"name": city, "count": 1}, timeout=10).json()["results"][0]
    w = requests.get("https://api.open-meteo.com/v1/forecast", timeout=10, params={
        "latitude": g["latitude"], "longitude": g["longitude"],
        "current": "temperature_2m,relative_humidity_2m,weather_code"}).json()["current"]
    return {"city": city, "temperature_c": w["temperature_2m"],
            "humidity_percent": w["relative_humidity_2m"], "weather_code": w["weather_code"]}

messages = [{"role": "system", "content": SYSTEM},
            {"role": "user", "content": "What's the weather like in Mumbai?"}]
raw = generate(messages, tools=tools)                    # Qwen via transformers chat template
for call in parse_tool_calls(raw):                       # empty list means answer directly
    result = get_weather(**call["arguments"])
    messages.append({"role": "tool", "name": call["name"], "content": json.dumps(result)})
answer = generate(messages, tools=tools)                 # Stage 5

The generate() helper and the exact cell layout are in the shared notebook. The SYSTEM prompt, parse_tool_calls regex and message roles are as shown on screen. weather_code 0 = "Clear sky" in the WMO code table.

Justification
  • The baseline run proves the point: without tools the LLM cannot know today's weather (stateless, training cut-off).
  • The system prompt is "the control we have": it tells the model when to use the tool.
  • Open-Meteo needs no key, so there are no secrets in the notebook and anyone can run it.
  • It is still a workflow: one tool, one call, no plan ⇄ act loop and no autonomy ("the level of liberty is not given").
Common mistakes
  • Thinking the LLM "calls the API". It only emits a structured request. Your code executes it.
  • Calling this a full agent. The professor said it is not: there is no reasoning or replanning loop.
  • Not guarding json.loads. Small models sometimes emit malformed JSON.
Professor emphasized
  • "LLM decides when to use the tool. This line is important."
  • "Without a tool, the LLM will hallucinate." The tool connection is described "using a JSON script". The JSON structures will be learned later.
  • "Change the models and observe."
"open Meteo" → Open-Meteo. "weather reagent" → weather agent. "temporary" → temperature or weather.
Extra reading
  • Open-Meteo Weather Forecast API docs: /v1/forecast, the current= variables and the WMO weather-code table (0 = Clear sky).

The LLM decides whether to call a tool

[2:01:54 – 2:04:28]
The concept

Even with the weather tool attached, "What is the capital of France?" produces tool_calls = [] (empty). The model knows this is general knowledge and answers directly. "What's the weather in Mumbai?" produces a get_weather call.

Intuition + layman analogy

A clerk with a phone does not call head office to ask "what is 2 + 2". They call only when they need information they don't have.

Scenario

Four questions sent to the weather agent expected behaviour

#QuestionTool call expected?
1What's the weather like in Mumbai?Yes: get_weather(Mumbai)
2What is the capital of France?No (shown in class)
3Is it humid in Chennai right now?Yes: get_weather(Chennai)
4Explain what humidity means.No: general knowledge
Step-by-step
1
Questions needing real-time data: #1 and #3. 2 tool calls
2
Questions answerable from training knowledge: #2 and #4. tool_calls = [] for both
3
Share of queries that hit the API. 2 / 4 = 50 %
2 API calls instead of 4fewer unnecessary calls means lower latency and cost
Justification
  • Letting the LLM decide whether to call a tool avoids pointless API calls. This is "LLM decides" behaviour, the seed of agentic autonomy.
  • A small model may mis-route, e.g. call the tool for #4 or skip it for #3. That is why observability is needed (Part 07).
Professor emphasized
  • "Though you are building a weather agent, you might ask a general question … no tool call happens. The LLM decides."
  • "This is a simple agent. The level of liberty is not given to the agent. It only finds the temperature."

🧠 Quick recall

1. In the restaurant exercise, which part is an LLM task and which is an agent task?
"Find a good Italian restaurant near my office open tonight" can be done by an LLM (with search). "Make a reservation for 2 at 7 PM" needs an agent, because it has to do a task.
2. Name the five stages of the weather notebook.
Baseline (no tools) → tool definition (schema) → tool selection (LLM emits <tool_call>) → execution (Open-Meteo) → response generation.
3. How much weight memory does a 7 B model need at BF16 and at 4-bit?
7 × 10⁹ × 2 B = 14 GB at BF16. 7 × 10⁹ × 0.5 B = 3.5 GB at 4-bit (plus KV cache and activations).
4. Why did "What is the capital of France?" produce no tool call?
The LLM judged that the question needs no external or real-time data, so it answered from its own knowledge and tool_calls was empty.
5. Why is the weather "agent" really a workflow?
It does one fixed thing: extract the city, call one API, respond. There is no plan ⇄ act loop, no retries or replanning, and no autonomy over a broader goal.
