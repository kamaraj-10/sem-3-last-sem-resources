The evolution journey (1960s – 2026)

[30:30 – 35:28]
The concept

Seven eras. Each solved the previous era's main limitation and introduced a new one.

EraTechnologyCapabilitiesLimitations
1960s–1990sRule-based (ELIZA, ALICE)Pattern matching, keyword detection, simple scripted Q&ANo learning, rigid, no context
2000–2010Statistical ML (SVMs, CRFs, HMMs)Intent classification, entity extractionLimited context, hand-crafted features
2010–2017Deep learning (RNNs, LSTMs, Seq2Seq, attention)End-to-end learning, better context understandingData-hungry, task-specific training
2017–2020Transformers (BERT, GPT-2, T5)Transfer learning, contextual embeddingsStill needs task-specific fine-tuning
2020–2023LLMs & generative AI (GPT-3, ChatGPT, Claude, PaLM)Few-shot learning, general-purpose, fluent generationHallucinations, no real-time data, no actions
2023–2025Agentic AI (LLMs + tools + memory + planning)Execute actions, multi-step reasoning, autonomous workflowsComplex orchestration, scaling, cost optimisation
2025–2026On-device & multimodal (SLMs, native multimodality)Real-time voice/video, privacy-first local processingHardware constraints, fragmented ecosystems
Key driver: the Transformer (2017), affordable GPU compute and internet-scale data together made LLMs possible. (Sources on slide: J&M Ch. 1; Vaswani et al. 2017.)
Intuition + layman analogy

Think of the evolution of navigation.

  • Rule-based: a printed list of fixed directions. If you leave the route, it is useless.
  • Statistical ML: a map with landmarks someone labelled by hand.
  • Deep learning: a driver who learned one city from lots of trips.
  • Transformers: a driver who learned driving in general and needs a short course for each new city.
  • LLMs: a fluent guide who knows every city from books but has no live traffic, sometimes invents roads, and cannot drive.
  • Agentic AI: that guide gets a car, a phone and a notebook, and plans the trip himself.
  • On-device: a smaller guide that lives in your phone and works offline.
Justification

Why each step happened

  • Rules → ML: rules could not generalise, so systems started learning intents and entities from data.
  • ML → DL: hand-crafted features were the bottleneck, so models moved to end-to-end learning.
  • DL → Transformers: every task needed its own big dataset, so models were pre-trained once and transferred.
  • Transformers → LLMs: fine-tuning per task was still needed, so scale enabled few-shot use with no task-specific training.
  • LLMs → Agents: LLMs hallucinate, lack real-time data and cannot act, so tools, memory and planning were added.
each era gains capability but adds cost and complexity. Agents bring orchestration, scaling and cost problems, and on-device models face hardware limits.
Common mistakes
  • Saying transformers removed fine-tuning. On the slide, transformers still require task-specific fine-tuning. Few-shot use without fine-tuning arrived with LLMs.
  • Listing "hallucination" as the only LLM limitation. The slide lists three: hallucinations, no real-time data, no actions.
Professor emphasized
  • ELIZA and ALICE: rule-based, predefined Q&A. When nothing matched they "very politely" said "I don't understand". There was no learning, no model, no neural network.
  • She described both as acting like a psychologist, in a medical context (board note: "Medical").
  • An LLM is a "pure intelligent reasoning model" but does not know current information and has no memory.
  • The course stops at agentic AI and multi-agent systems. On-device and multimodal is an active research area, not course scope.
"Elisa / Alice" → ELIZA / ALICE. "RN and cell st… sequence to sequence" → RNN, LSTM, Seq2Seq. "few short learning" → few-shot. "agent KI" → agentic AI. "when you add Ml with the tools" → when you add an LLM with tools. "more 300 words only" is unclear in the audio .
Beyond the lecture
  • ELIZA (Weizenbaum, 1966) ran the "DOCTOR" script, which imitates a Rogerian psychotherapist. ALICE (Wallace, 1995) was a general-purpose AIML-based chatbot rather than a medical one .
  • J&M SLP3 Ch. 1: the historical overview the slide cites.
rules → statistical ML → deep learning → transformers → LLMs → agents → on-device. The Transformer, GPUs and web-scale data were the turning point.

Intent & entity (class discussion)

[31:50 – 33:10]
The concept

Intent = what the user wants. Entity = the things it is about.

Statistical ML chatbots (SVM, CRF, HMM) were built around two tasks: intent classification and entity extraction.

Turn a free-form sentence into an action plus its parameters.
Intuition + layman analogy

Filling in a form at a bank counter. The form type is the intent ("withdrawal", "deposit"). The boxes you fill in are the entities (account number, amount). The clerk listens to your sentence and decides which form to use and what goes in each box.

Definition
utterance  →  ( intent, { entity1, … , entityk } )
  • intent the user's goal. It is a label from a fixed set and is often signalled by the verb.
  • entityi a typed span (place, date, product). Often found among the nouns (POS tagging is a cue).
  • k number of entities found (0 or more)
Scenario

"Book a flight from Bengaluru to Delhi tomorrow" illustrative

TokenPOS
BookVB (verb)
flightNN (noun)
Bengaluru, DelhiNNP (proper nouns)
tomorrowNN (time noun)
Step-by-step extraction
1
Verb "Book" + object "flight" gives the intent. intent = book_flight
2
Proper noun after "from" is the source. source_city = Bengaluru
3
Proper noun after "to" is the destination. destination_city = Delhi
4
Time word. date = tomorrow
book_flight(source=Bengaluru, dest=Delhi, date=tomorrow)
Justification
  • Verbs map to actions and nouns map to arguments. That is why POS tags were good cues for SVM/CRF systems.
  • The features are hand-crafted and the context is limited. "Change it to Friday" in the next turn breaks this approach. That limitation motivated the next eras.
Professor emphasized
  • Student answer, accepted: intent is "what the user wants to know". The entity is the category or relation it belongs to.
  • With POS tagging, the verb can be identified as the intent and the nouns as entities.
"PIYUSH tagging" → POS tagging (part-of-speech).
an intent is a verb-like goal and entities are noun-like parameters. Classical chatbots were essentially intent classifiers plus entity extractors.

The three levels of conversational AI

[35:28 – 36:26]
The concept

From scripted responses to goal-directed autonomy. The levels differ in how much initiative and control the system has.

Tell the levels apart by asking who has initiative and control: the script, the developer's code, or the LLM.
Intuition + layman analogy

L1 · Vending machine

Press B4 and you get chips. Press anything else and nothing happens.

L2 · Trained clerk with a manual

Understands you, looks things up and uses the phone, but follows the manual step by step.

L3 · Personal assistant

"Get me to Delhi on Friday." They decide how and fix problems as they come up.

Professor emphasized
  • Rule-based: answers by keyword, with no learning or training. It runs on scripts and decision trees and has limited context.
  • An LLM-powered assistant already has tool calling and memory (and RAG), but it is still not an agent. See the next topic.
Level 1 answers questions, Level 2 assists with tasks, Level 3 manages outcomes.

LLM-powered assistant (workflow) vs autonomous agent: who makes the plan?

[36:26 – 42:59]
The concept

An LLM with tools + memory is an augmented LLM. It becomes an agent only when the LLM itself plans.

LLM-powered assistant = workflow

  • The plan is written in code by the developer: "call this tool, then fetch this memory, then respond".
  • No planning or reasoning about the steps by the LLM.
  • For closed-ended problems.

Autonomous AI agent

  • The developer gives a goal + a list of tools + memory.
  • The LLM decides which tool to call when, observes the result and revises. It retries within an iteration limit (e.g. 5).
  • For open-ended problems. Complex tasks can be split across multiple agents.
Ask "who writes the plan?" Code means workflow (augmented LLM). The LLM means agent.
Intuition + layman analogy (professor's own)

A personal assistant. You give them money and say "book the ticket and plan the trip". You do not say "come at 8:00, take the vehicle, go here, then there". Spelling out every step is the workflow. Handing over the goal and the means is the agent.

Embedded-dev lens

A workflow is a fixed sequence in main(): read_sensor(); filter(); send();. An agent is a scheduler or state machine whose next state is chosen at runtime by a policy (here, the LLM), with a watchdog limiting iterations.

Definition
Augmented LLM = LLM + tools + memory (+ retrieval)   |   Agent = Augmented LLM + autonomy (LLM plans)
  • tools external functions or APIs: the "hands"
  • memory conversation history and stored user facts
  • autonomy the LLM is allowed to decide the sequence of actions, observe, and retry up to an iteration limit N (the example in class was 5)
The term "augmented LLM" is Anthropic's (Claude). It is still not an agent.
Scenario

Retry budget of an agent beyond lecture: why an iteration limit helps

GivenValue
Probability a single attempt solves the sub-task, p0.4
Iteration limit N (from class)5
Assumptionattempts independent
Step-by-step computation
1
Probability that one attempt fails. 1 − p = 1 − 0.4 = 0.6
2
Probability that all 5 attempts fail. 0.6⁵ = 0.6 × 0.6 × 0.6 × 0.6 × 0.6 = 0.07776
3
Probability of success within 5 attempts. 1 − 0.07776 = 0.92224
≈ 92.2 % vs 40 % for a single fixed attempthigher is better, but each retry costs tokens
Justification
  • Agents handle open-ended tasks where the steps cannot be known in advance.
  • Observe → revise loops recover from errors, as the retry calculation shows.
  • Less predictable, and every loop iteration costs tokens and latency. That is why an iteration cap is needed.
  • For closed-ended tasks, a workflow is simpler, cheaper and easier to test.
workflow = control and predictability. Agent = flexibility and autonomy. Choose based on how open-ended the task is.
Code (sketch) 
# WORKFLOW: the developer hard-codes the plan
def assistant(query):
    weather = get_weather(extract_city(query))          # step 1 fixed
    prefs   = memory.load(user_id)                      # step 2 fixed
    return llm(f"{query}\n{weather}\n{prefs}")          # step 3 fixed

# AGENT: the LLM chooses tools in a loop, capped at N iterations
def agent(goal, tools, N=5):
    history = [goal]
    for _ in range(N):
        step = llm.decide(history, tools)               # returns {"tool":..., "args":...} or {"final":...}
        if "final" in step:
            return step["final"]
        obs = tools[step["tool"]](**step["args"])
        history.append(obs)                             # observe, then revise next turn
    return "Stopped: iteration limit reached"
Common mistakes
  • "It has tools and memory, so it's an agent." Wrong. Without LLM-driven planning it is an augmented LLM, i.e. a workflow.
  • Forgetting the iteration limit. An unbounded agent loop can burn tokens forever.
Professor emphasized
  • "Here the plan is done by code. Here the plan is done by the LLM itself. That's the fundamental difference."
  • "We are hard-coding it" (assistant) vs "we will give the list of tools, and the agent itself will decide which tool to call when".
  • "If it goes wrong, it will try again several times. If I set the iteration to five, that's autonomy."
  • Board notes: Level 2 = workflow, closed-ended, no plan, gives a response. Level 3 = LLM → plan, open-ended problems.
"as per Cloud" → as per Claude (Anthropic). "Ml powered assistant" → LLM-powered assistant. "autonomous AI adjustance" → autonomous AI agents. "a context server tool enabled" → context-aware, tool-enabled. "very good, Troy" → "very good, try".
Extra reading
  • Anthropic – Building effective agents: "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents are systems where LLMs dynamically direct their own processes and tool usage." This matches the professor's distinction exactly.
  • Wang et al. survey (cited on the slide as 2024): the planning, memory and action modules of LLM agents.
tools + memory make an augmented LLM (a workflow). Giving the LLM autonomy to plan, act, observe and retry makes it an agent.

Q&A: Is MCP an agent? Is an LLM an agent?

[42:59 – 46:40]
The concept
  • MCP is a protocol, not an agent. It is a standard way to connect an LLM application to tools and external parties, "like your USB". You can use it in workflows and in agents.
  • An LLM by itself is not an agent. "LLM is purely a model." You build an agent from an LLM by giving it autonomy.
Intuition + layman analogy

USB vs the person using the computer. USB lets any keyboard, printer or drive plug in the same way, but USB does not decide what to print. MCP is the plug. Whether the system is an agent depends on who decides which plugged-in tool to use. Like HTTP, it is a standard that anyone can use anywhere.

Justification
  • Without MCP you write separate integration code for every tool. With MCP, one connection reaches all the tools on a server.
  • Where the tool list comes from (MCP or hard-coded) is a separate question from who plans. Keep the two questions apart.
Common mistakes
  • "I used an MCP server, so I built an agent." Not necessarily. MCP only standardises access.
  • "LLM = agent." The LLM is the reasoning engine inside the agent. Autonomy is what turns it into an agent.
Professor emphasized
  • "MCP is like your USB": a standardised way to connect with tools. It is not only for AI agents.
  • When the MCP client lets the LLM choose among the tools without the developer dictating the order, that is agent-like behaviour. She confirmed this to the student and promised a code demo of turning an LLM-powered assistant into an autonomous agent.
"SMPC server" → MCP server. "SLM powered assistant" → LLM-powered assistant. "HTP" → HTTP.
Extra reading
  • MCP – official intro: "Think of MCP like a USB-C port for AI applications". The official docs use the same analogy as the professor.
MCP is plumbing and the LLM is the engine. Autonomy in planning is what makes it an agent.

🧠 Quick recall

1. What three limitations of LLMs (2020–2023) does the slide list?
Hallucinations, no real-time data, no actions.
2. What was the "key driver" that made LLMs possible?
The Transformer (2017), affordable GPU compute and internet-scale data, together.
3. An app always calls a search API, then the LLM, then returns the answer. Agent or not?
Not an agent. The plan is fixed in code, so it is an LLM-powered assistant (augmented LLM, workflow).
4. Single-attempt success p = 0.5, iteration limit 3. What is P(success)?
1 − 0.5³ = 1 − 0.125 = 0.875 (assuming independent attempts).
5. Is MCP an agent?
No. It is a standard protocol for connecting LLM applications to tools ("like USB"), and it can be used in workflows or agents.
