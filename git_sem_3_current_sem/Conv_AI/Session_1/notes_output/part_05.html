Transformers & LLMs: the brain

[1:04:34 – 1:08:12]
The concept

Every conversational agent is built on an LLM, and every LLM is built on the Transformer

Technical capabilityImpact on conversations
Self-attention: relates every word to all others in the input→Ambiguity handling: resolves unclear or underspecified requests
Contextual understanding: word meaning depends on surrounding context→Intent understanding: grasps user goals from context
Long-range dependencies: connects ideas across very long passages (the context window)→Multi-turn coherence: remembers and tracks earlier parts of the chat
Parallel processing: faster training than RNNs, enabling massive scale→Natural responses: fluent, human-like (indirectly, through scale)
Key insight: each internal capability of the Transformer shows up as a visible conversational behaviour.
Intuition + layman analogy
  • Self-attention is a meeting where every participant listens to every other participant before speaking, so "it" in "put the cake in the oven until it is golden" is linked to the cake, not the oven.
  • Context window is the size of the whiteboard. Anything that does not fit on it is invisible to the model.
  • Parallel processing: an RNN reads a book one word at a time. A Transformer spreads all pages on a table and reads them at once.
Formula / rule of thumb

How much fits in a context window?

W ≈ 0.75 × T     P = Wwpage     Nturns = Ttturn
  • T context window size in tokens
  • W approximate English words. 0.75 words per token is a common rule of thumb for English, and it varies by tokenizer and language .
  • wpage words per page (≈ 500 for a dense page)
  • tturn tokens per query + response pair
Scenario

A 2-million-token context window (the figure quoted in class)

Justification
  • A large window lets you upload a document and hold a long, coherent multi-turn chat about it.
  • Contextual embeddings fix the static-embedding problem (word2vec, GloVe, CBOW give one vector per word).
  • Even 2M tokens is finite. Past the window the model forgets, which is why external memory is needed (topic 4).
Common mistakes
  • Treating "tokens" as "words". A token is a sub-word unit (covered later today).
  • Assuming every model has a 2M window. Sizes vary widely by model and version .
Professor emphasized
  • Pre-training alone is not sufficient. Fine-tuning or instruction tuning follows (details later). Then tools, extra books (memory) and planning turn the model into an agent.
  • "No more word2vec, GloVe and CBOW giving static embeddings": here meaning depends on context.
  • Board: "context → 2M". The long-range dependency is what lets the model see up to that many tokens.
"what to wake / glow / see bow" → word2vec / GloVe / CBOW. "Cloud, LLAMA" → Claude, Llama. "with applaud" → with Claude. "NLM can see" → LLM can see.
Beyond the lecture: the self-attention equation
Attention(Q, K, V) = softmax ( Q KT√dk ) V
  • Q, K, V query, key and value matrices (one row per token)
  • dk key dimension. Dividing by √dk keeps scores from growing with dimension.

Tiny example: one query, two keys, with q·k₁ = 2, q·k₂ = 0 and dk = 4. Scaled scores: 2/2 = 1 and 0/2 = 0. Softmax: e¹/(e¹+e⁰) = 2.718/3.718 = 0.731 and 1/3.718 = 0.269. With scalar values v₁ = 10 and v₂ = 2, the output is 0.731×10 + 0.269×2 = 7.31 + 0.54 = 7.85, pulled toward the more relevant token.

  • Vaswani et al. 2017 – Attention Is All You Need (cited on the evolution slide)
Transformer mechanics (attention, context, long range, parallelism) are what make LLM conversations disambiguating, intent-aware, coherent and fluent.

LLM capabilities and limitations

[1:08:12 – 1:10:36]
The concept

An LLM is stateless but a very good reasoner (that reasoning comes from training)

✅ What LLMs do well

  • Natural conversation: human-like dialogue
  • Intent understanding: grasp user goals
  • Context retention: multi-turn conversations
  • Generation: fluent, contextual replies
  • Summarization: condense information
  • Entity extraction: identify key information
  • Sentiment analysis: detect user emotions

✗ LLM limitations

  • No real-time data: training cut-off date
  • Hallucinations: plausible but false output
  • Can't act: no access to external systems
  • No memory: forgets after the context window
  • Calculation errors: struggles with maths
  • Inconsistency: varying answers to one question
  • No verification: can't check facts

Source on slide: Bommasani et al. (2021).

Intuition + layman analogy

A brilliant goldfish with an encyclopedia memorised up to 2025. It talks beautifully and summarises anything, but it doesn't know today's news, can't pick up a phone, forgets you once the conversation scrolls away, and sometimes recites an entry that never existed.

Justification
  • Every item on the right-hand list maps to an augmentation in the next topic. That mapping is the reason for building an agentic architecture.
Common mistakes
  • Confusing "context retention" (a strength, within the window) with "no memory" (a limitation, beyond the window). Both are true at once.
Professor emphasized
  • Board: "LLM → stateless → [needs] memory". "Very good reasoning capability ← training".
  • "If the model is trained till 2025, it knows only what happened till 2025."
  • Entity extraction and sentiment analysis come by default, because the LLM is a good reasoning model.
"understand intense" → understand intents.
Extra reading
  • Bommasani et al. – On the Opportunities and Risks of Foundation Models (slide source)
an LLM is a stateless, very capable reasoner with seven systematic weaknesses. Each one needs an external fix.

Why we need agentic architecture

[1:10:36 – 1:11:42]
The concept

Solution: augment LLMs with external capabilities

LLM limitationAgentic solutionExample
No real-time dataTool calling (APIs, search)Check current flight prices
HallucinationsRAG (retrieval-augmented generation): groundingGround answers in company docs
Can't take actionsFunction calling (also called tool use)Book appointment, send email
No memoryExternal memory systemsRemember user preferences
Calculation errorsCalculator tool, code executionPrecise maths computations
Plus reasoning and planning (board: "Reason/plan → ReAct"), the Reasoning + Acting capability. Sources: Lewis et al. 2020 (RAG); Yao et al. 2023 (ReAct).
Intuition + layman analogy

Back to the student locked in a room: give them a phone (tools / real-time data), the company handbook (RAG), a pen to sign forms (function calling), a diary (memory) and a calculator. Then teach them to think before acting (ReAct).

Embedded-dev lens

You don't make the CPU do floating point in software when there is an FPU. In the same way, you don't make the LLM do arithmetic "in its head" when a calculator tool exists. Offload to the right peripheral.

Professor emphasized
  • In 2020–2023, ChatGPT "confidently gave wrong answers" to maths questions. Now it can call a calculator or execute code for precise computation.
"argument LLMs" → augment LLMs. "Excel memory systems" → external memory systems. "the react tool" → ReAct (reasoning + acting).
Extra reading
  • Lewis et al. 2020 – Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks: combines parametric memory (the seq2seq model) with non-parametric memory (a dense Wikipedia index).
  • Yao et al. – ReAct
each LLM limitation has a matching augmentation (tools, RAG, function calling, memory, calculator), and ReAct-style reasoning ties them together.

Q&A: what is "external memory" if we already have RAG?

[1:11:42 – 1:18:46]
The concept

RAG grounds answers in a document. Memory systems remember you and past interactions.

Short-term memory

Within one instance or episode, i.e. the current conversation.

Long-term memory (3 kinds)

  • Semantic: facts and preferences ("user codes in Rust")
  • Episodic: what happened in earlier conversations (a chat from a month ago)
  • Procedural: how to do things (skills, procedures)
RAG is a storage-and-retrieval mechanism and can implement some memory, but grounding alone is not enough.
Intuition + layman analogy

RAG is the open textbook on your desk during an exam: answers come from that book. Memory is your personal tutor who knows you always code in Rust, remembers last month's doubts, and knows your preferred way of solving problems.

Scenario (from the board)

Company HR bot, with and without the HR policy document

SetupQueryWhat the bot does
LLM-based HR bot, no company HR docs"How many casual leaves do I get?"Gives a generic HR answer based on general reasoning
Same bot with the HR policy PDF (RAG)Same queryLooks it up in the PDF and gives a company-specific, grounded answer
Bot with RAG + memory"Write a script for this"Answers in Rust without asking, because the stored preference says the user codes in Rust
Step-by-step: which mechanism answers what
1
Is it company-specific knowledge? → RAG (grounding in documents).
2
Is it about this user's preferences? → Long-term semantic memory.
3
Is it about what happened in an earlier chat? → Episodic memory.
4
Is it about how to carry out a known procedure? → Procedural memory (e.g. skills).
5
Is it about earlier in this conversation? → Short-term memory (context window).
RAG = grounding · Memory = personalisation + continuity
Common mistakes
  • "RAG is the memory system." RAG is one mechanism. You still need short-term, semantic, episodic and procedural memory for a personalised assistant.
Professor emphasized
  • "RAG is a kind of memory, I agree, but it is used to ground your answer in the particular document."
  • Earlier you had to say "write this in Rust". Now ChatGPT and Claude remember your preference, because user preferences are stored in memory.
  • Every memory type will have a hands-on session later.
"Other than rank" → other than RAG. "Chat GPD" → ChatGPT. "Excel memory" → external memory.
use RAG for "what does the document say" and memory for "who is this user and what happened before". A real assistant needs both.

An AI system ≠ an LLM

[1:18:46 – 1:19:40]
The concept

Memory, RAG and tools are not "inside the model you choose". They are parts of the AI system you build. "In the AI system, the LLM is just one component." Board: AI system ⊃ LLM + other boxes.

Intuition + layman analogy

The LLM is the engine. An AI system is the whole car: fuel tank (data), steering (planning), brakes (safety), dashboard memory (preferences). Buying the best engine doesn't give you a car.

Professor emphasized
  • "An AI system is not always equivalent to an LLM. An agent is not equivalent to an LLM." You must decide which kinds of memory your system needs.
designing conversational AI means designing the system around the LLM, not just picking a model.

Agent lifecycle: request → response (7 stages)

[1:19:40 – 1:22:24]
The concept

Seven stages. Reasoning ↔ tool invocation repeats as a loop until the goal is met (ReAct).

Intuition + layman analogy

A hospital visit. Reception checks your ID (request). Triage sends you to the right department (routing). The doctor thinks about what tests are needed (reasoning) and orders them (tool invocation), maybe several rounds. The file is updated (memory), the report is reviewed for errors and privacy (safety), and you get the prescription in a form you understand (response).

Scenario (professor's example)

Weather agent: "Check the weather and plan my Saturday evening in Bangalore"

The weather API may fail. The agent retries the same API, and after two failures switches to a different weather API. illustrative probabilities below

GivenValue
P(API-A call succeeds), each try0.7
Tries on API-A before fallback2
P(API-B call succeeds)0.9
Assumptionindependent attempts
Step-by-step computation
1
Probability API-A fails once. 1 − 0.7 = 0.3
2
Probability API-A fails both tries. 0.3 × 0.3 = 0.09
3
Probability fallback API-B also fails. 1 − 0.9 = 0.1
4
Probability everything fails. 0.09 × 0.1 = 0.009
5
Probability the agent gets the weather. 1 − 0.009 = 0.991
99.1 % vs 70 % with a single fixed callhigher is better, at the cost of up to 3 calls
Justification
  • The reasoning ↔ tool loop is what makes an agent robust to flaky real-world APIs.
  • Safety comes before the response, so toxic content or PII never reaches the user.
  • Each retry adds latency and cost. An iteration cap is needed.
reliability (more retries and fallbacks) vs latency and cost (fewer calls).
Code (retry + fallback sketch) 
def get_weather(city, apis, tries_per_api=2):
    for api in apis:                         # e.g. [api_a, api_b]
        for _ in range(tries_per_api):
            try:
                return api(city)                  # observe success
            except (TimeoutError, ConnectionError):
                continue                         # reason: retry, then fall back
    return None                                 # let the agent tell the user it failed
Common mistakes
  • Reading the 1–7 numbering as a strict pipeline. It is a conceptual order. Stages 3 and 4 loop, and memory and safety can act at several points.
  • Dropping the request stage's validate & sanitize step. It is the first defence against prompt injection.
Professor emphasized
  • Board: "Numbering → not a strict order." "AI system ⊃ LLM."
  • "It is not always that the connection will be established and the weather API is working … It will not stop … it will try the other weather API. There will always be a loop."
Extra reading
  • Wang et al. survey (R1) and ReAct, the slide's sources for the lifecycle.
request → routing → (reasoning ⇄ tool invocation) → memory → safety → response. The ReAct loop gives agents their robustness.

🧠 Quick recall

1. Map the four Transformer capabilities to their conversational impact.
Self-attention → ambiguity handling. Contextual understanding → intent understanding. Long-range dependencies → multi-turn coherence. Parallel processing → natural responses (through scale).
2. A 128,000-token window at 0.75 words per token and 500 words per page holds how many pages?
0.75 × 128,000 = 96,000 words, and 96,000 / 500 = 192 pages.
3. Give the agentic solution for each LLM limitation: real-time data, hallucinations, actions, memory, maths.
Tool calling (APIs, search), RAG, function calling (tool use), external memory systems, calculator tool / code execution.
4. Name the three long-term memory types and give an example of each.
Semantic (user codes in Rust), episodic (last month's conversation), procedural (skills, e.g. Claude Skills).
5. List the seven lifecycle stages. Which two loop?
Request, routing, reasoning, tool invocation, memory, safety, response. Reasoning ⇄ tool invocation loop (ReAct).
